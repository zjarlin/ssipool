# 两端暂停后的时钟恢复实验

本轮只覆盖两个专用 PF24 VM 在同一物理 ESXi 上的有限暂停恢复。它们仍须分别收到 QMP `stop`；一次 `stop` 不会自动停止整个分布式客体。Ceph、跨物理容量、Docker 和 PostgreSQL/Redis 接管尚未实现，业务主机与磁盘没有加入实验。

## 实现的边界

旧运行时在第二次启动时直接报告 `cold start only`。新候选利用 x86 KVM 的 `pre_resume_vm` 钩子，在 QEMU 设置 RUNNING、发送 RESUME 和放行 vCPU 之前完成恢复准备：

1. 只接受双节点、完整用户暂停、所有本进程 vCPU 已停的状态。单步、重置后恢复和其他迁移状态拒绝执行。
2. 为本轮递增代际。双方确认已进入准备阶段，交换暂停后读取的 KVM 时间和 TSC 下界。
3. 源端保留连续的 KVM 时钟；目标重新获取 16 份快照，保留原生频率相同、最小 RTT 不超过 5 ms 的原门槛。两边分别设置并读回 TSC offset；恢复时拒绝本实例各 vCPU 偏移不一致。
4. 准备后的 KVM/TSC 读数必须不低于双方的下界。双方再次确认时钟准备完成，才分别返回启动路径。

本候选保留暂停期间继续推进的原生 TSC，并据此推进 KVM 时间；它没有承诺“暂停多久，客体时钟就冻结多久”。当前定时器检查是在最终恢复后新建的四个 20 ms 定时器，尚未验证暂停前已挂起的各种定时器、设备计时或应用租约。

KVMCLOCK 请求和回复携带代际，快照发布受互斥锁保护；路由接收线程不获取 BQL 或等待运行中 vCPU。恢复屏障还检查版本、方向、阶段及重复消息。协议版本为 4，**两端必须部署完全相同的运行时哈希**；没有跨重连认证，也不能抵御恶意节点。

这个屏障保证的是放行前双方均已完成准备，不保证分区时“同时开始、同时继续”。冷启动依然沿用源端先发布的已有流程：尝试给冷启动也加双向屏障曾令两端在主循环接收连接之前互等，该失败记录保留。它不能因此被称为全生命周期启动协议。

## 超时不能依赖正常退出回调

主线程可能持有 BQL 阻塞在网络读取。第一版独立超时线程虽然在 15 秒后调用 `exit(1)`，但 QEMU 的 `qemu_run_exit_notifiers()` 又要获取 BQL，导致超时线程也卡住。

真实无响应对端实验的 GDB 栈同时记录了：主线程位于 `kvmclock_barrier → qemu_get_be32 → recvmsg`，超时线程位于 `cluster_clock_watchdog → exit → qemu_run_exit_notifiers → bql_lock_impl`。旧候选最终被采集器 SIGKILL，不能算自行失败停止。

候选改为在准备超时记录错误后执行 `_exit(1)`，避开用户态正常退出回调。这是不可恢复协议失败后的停止路径，**不执行应用刷盘、不宣称数据库一致性、不提供接管**。其他内核阻塞、进程处于不可中断状态、全机宕机与任意运行态网络分区仍有待独立验证。

## 证据与失败记录

[脱敏原始记录](evidence/ssi-clock-resume-20261107.json) 保留 QMP 请求/回复与事件、两个节点的时钟阶段、客体连续采样、进程退出、宿主日志、二进制和采集器哈希。私有原始文件的哈希独立保存，公开内容删除主机地址与私有路径。

`guest-clock --pause-rounds` 在同一进程中保留上一轮 TSC、MONOTONIC、MONOTONIC_RAW、BOOTTIME，每一轮输出等待标记，协调器在两端真正暂停和恢复后才允许下一轮读取。检查器同时关联七对 STOP/RESUME 事件、暂停/运行快照、代际 2–8、每轮 16 次新采样及双方共享的时钟下界；不会根据一条完成日志判定成功。

最终候选二进制为 `ea2e1852d1318fc9e92663be4bab6d1cf55978998ea16ade662cc8bc6639ad7d`。完整七轮恢复实验的四个定时器最大 **37.85 ms**，未改变原 250 ms 门槛；客体进入 S5、两端自行退出 0，没有强制清理。静默对端实验的主端在约 **15.40 秒**自行失败退出；此时对端仍被实验 SIGSTOP 暂停。解除暂停后，对端报告 `SSI invalid clock barrier` 并自行退出 1，不能写成观察到了 EOF，也不能把它描述成两台故障主机同时完成了有界关闭。

历史记录仍包括：旧版首次恢复拒绝；第一版冷启动互等；直接 QMP quit 时排空后仍产生流量的退出 1；采集器停止读取串口时的关机超时；以及交换节点角色后出现 `Long readout interval, skipping watchdog check` 的失败。该反向实验虽然完成七轮读数、定时器和关机，仍不通过整体日志门槛。它出现在首次暂停之前，不能据此归因于恢复算法，也不能忽略。

验证命令：

```sh
python3 scripts/ssi-lab/check-clock-resume.py docs/evidence/ssi-clock-resume-20261107.json
python3 -m unittest discover -s scripts/ssi-lab -p 'test_clock_resume.py'
```

补丁 `experiments/qemu-clock-resume.patch` 在 `qemu-reset-router.patch` 之后应用，许可 GPL-2.0-or-later，不进入默认生产安装。只修改 QEMU；宿主仍为 PF24，实验结束后恢复原版内核。

## 仍未解决

- 单一全局暂停命令，以及设备、内核异步生产者和在途 I/O 的完整停止协议。
- 重置、重连、迁移、频率缩放、跨物理频率漂移与长期同步。
- 直接 QMP quit 的全部设备停止顺序，以及 DSM seal、CLOSE/ACK 和干净断连。宿主关闭日志仍会出现 `ktcp_receive` 错误。
- 扩展到独立物理机、超单机内存容量和新增磁盘；无 RAID 的 Ceph 副本与恢复尚未部署。
- 业务容器持久化、PostgreSQL/Redis 恢复、sub2api 稳定运行与自动接管。

因此父场景保持 `@partial`，本轮只单独标记已完成的受限恢复与拒绝路径。
