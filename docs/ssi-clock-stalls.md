# PF28 活动客体时钟与取页观测

2026-11-08，在同一物理 ESXi 的两个专用 PF28 VM 上重复运行 SSH、三轮跨 CPU 时钟检查、四线程内存校验、用户态暂停和 1 MiB SFTP。三次均完成客体关机与两端原生关闭检查，但 workqueue 告警仍存在，第二次还出现约 1.228 秒的 watchdog readout interval。**最终采集中的一个 20 ms 定时器耗时 445.409 ms，超过原 250 ms 门槛；没有修复长停顿，也没有通过完整 SSI 验收。** 本轮没有更改内核、QEMU、时钟策略或验收门槛。

## 测量结果

最终采集在 SSH 就绪后开始，SFTP 结束后停止；两个宿主各使用独立的全局跟踪时钟，不能把两个宿主的时间戳直接相减。跟踪结束后才启动已有的原生关闭采集。

| 项目 | 节点 0 | 节点 1 |
| --- | ---: | ---: |
| 标记之间的窗口 | 48.201 s | 47.346 s |
| 完整捕获事件，含窗口外启停边界 | 584,643 | 564,711 |
| 窗口内完整页面获取调用 | 292,319 | 282,353 |
| 页面获取中位数 | 86 μs | 89 μs |
| 页面获取 p95 | 329 μs | 314 μs |
| 页面获取最大值 | 29.098 ms | 29.190 ms |
| 观测到的 `kvm_guest_time_update` 调用 | 0 | 0 |
| 末尾没有记录返回的调用 | 1 | 1 |

最长取页调用均来自 `direct_page_fault`。这些是宿主函数入口到返回的墙钟耗时，包含网络、调度与虚拟化停顿，不是有效 CPU 执行时间。取页延迟与客体 workqueue 的累计耗时也不是同一个指标。

三次运行各有十二个 20 ms 定时器，最大值分别为 64.161、46.823、445.409 ms。前两次通过有限定时器门槛，最终一次失败。探针输出 `CLOCK_PASS` 只代表其内建检查通过；控制端仍须用原 250 ms 门槛复验，不能把进程退出零写成时钟验收通过。

零次时钟更新只适用于这两个启动后的短窗口。它不能证明启动、暂停恢复、早期 watchdog 告警、长期漂移或跨物理机时钟没有问题。单次取页最大值也不足以解释或排除长停顿；下一步仍需把客体 workqueue 的执行区间与累计取页、宿主调度关联起来。尚未验证的 steal-time 缓存写入线索没有作为本轮结论或修复。

## 活动探针的边界

旧关闭采集器面向已退出的 QEMU。直接用它观察仍运行的客体，会在冻结缓冲区后、导出期间继续累计探针命中；第一次记录因此被严格计数检查拒绝，未用于最终延迟统计。

新采集器先打开缓冲区再启用探针，结束时先停用事件再冻结缓冲区。第二次实验确认，返回探针还有一个合法边界：已经进入函数的调用可在停用后到达 `kretprobe_dispatcher`。PF28 的该函数先增加 `nhit`，再检查 `TP_FLAG_TRACE`，所以返回命中数可能比实际事件多。第二次记录保留为仪器中间结果，最终采集增加了 QEMU 与所有线程的起止身份记录。

`check-clock-stalls.py` 因此使用明确的活动调用检查规则，原关闭检查器保持不变：

- 入口命中数必须与事件数完全一致；缓冲区头部、逐 CPU 计数、零丢失和零 missed 均须通过。
- 按线程配对入口和返回。内部孤立返回、重复入口、vCPU 指针变化或 PID 复用直接失败。
- 返回命中差只能介于零和末尾尚未返回的调用数之间，单独报告，不能用来补造返回时间。
- 窗口前的孤立返回、末尾未完成调用，以及跨越标记的完整调用均不进入窗口内耗时分布。
- 采集通过只表示记录满足检查规则，不自动证明停顿根因或运行时正确。

## 使用与证据

先看 `trace-clock-stalls.py` 的目标检查，再用 `check-clock-stalls.py` 分析新文件。采集器只接受独占 PF28 x86 节点、明确命名的 SSHPool QEMU、属于指定节点的 DSM 线程与空闲 tracefs。控制端等待 `ready`，发送 `stop\n` 结束；超时会报告失败并清理自身探针。

```sh
sudo python3 scripts/ssi-lab/trace-clock-stalls.py \
  --pid QEMU_PID --node 0 --output NEW_TRACE.json
python3 scripts/ssi-lab/check-clock-stalls.py NEW_TRACE.json
python3 -m unittest discover -s scripts/ssi-lab -p 'test_clock_stalls.py'
```

远端需要同目录的原有 `probe-kernel-close.py` 及其依赖，部署时核对整个实验工具集合。全量私有跟踪的本地回放另指定：

```sh
SSHPOOL_CLOCK_STALL_TRACE_DIR=/path/to/private/evidence \
  python3 -m unittest discover -s scripts/ssi-lab -p 'test_clock_stalls.py'
```

[公开证据](evidence/ssi-clock-stalls-20261108.json) 包含三次完整客体日志、时钟与内存日志、两端原生关闭跟踪、防火墙前后快照、仪器失败计数、最终跟踪哈希及最长调用端点。约 115 万条最终时钟事件保留在私有实验目录，**公开端点不是全量跟踪，CI 也不冒充全量重放**；提供私有目录时，测试先验证哈希再重算全部统计。普通 CI 校验公开端点、关闭协议、工作负载、告警保留与合成损坏记录的拒绝路径。

实验结束后，两台 VM 均恢复 `6.8.0-147-generic`，启动文件与 GRUB 配置未变，防火墙恢复原样，进程、跟踪与实验 TCP 无残留。原先运行的 Lima 保持运行。跨物理容量、持久化、Ceph、Docker 与数据库恢复仍未完成。
