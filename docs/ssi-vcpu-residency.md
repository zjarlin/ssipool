# KVM 停顿观测与 PAUSE 实验

2026-11-06。PF14 增加默认关闭的 DSM PAUSE 拦截实验开关。两个专用 x86 VM 仍在同一物理 ESXi 上，客体仍是原版 Ubuntu 内核、无持久磁盘的 SSH 工作区。**这不代表稳定 SSI、跨物理机容量相加、Docker、Ceph、数据库或故障接管已经完成。**

## 从调度等待定位到客体循环

取消实验 VM 的 CPU 限额后，PF11 仍出现长等待。本轮同时记录 KVM 进入退出、宿主本地定时器、其他中断和所有宿主调度事件。PF11 两侧完整记录分别包含 2,054,136 和 2,105,637 个事件，没有缓冲丢失。最长 KVM 区间分别为 7,983.207 和 3,111.166 ms；节点 0 对应的 DSM 可运行等待为 7,984.102 ms。

这些区间内，同一宿主 CPU 没有记录到本地定时器中断。同期 ESXi 的 CPU 限速与 co-stop 计数为零，ready 最大值为每个 20 秒汇总窗口 31/46 ms。这些管理层汇总不能精确归因每个微观停顿，但不能继续把已解除的 CPU 限额当作现有解释。

客体以 `nokaslr` 启动。使用同一客体内核的 System.map 和实际解压 ELF 反汇编，长区间的指令地址落在 `ktime_get` 与 `ktime_get_update_offsets_now` 的 seqcount 读取循环：读到奇数版本时执行 `PAUSE`，等待写入者完成。它与 DSM 线程等待同时出现，不能仅凭静态指令地址断言整个区间始终执行同一条指令。

`kvm_entry` 位于 VMCS 准备与 LAPIC 等待之前，`kvm_exit` 位于实际退出后的部分处理之后。因此分析器报告的是 **KVM 进入退出边界区间**，不把它直接算成有效客体执行时间。该轮没有捕获到 `kvm_wait_lapic_expire` 事件；本实验没有增加函数探针，也没有直接测出 ESXi 内部各段耗时。

## PF14 的范围

在 PF11 上应用 [候选补丁](../scripts/ssi-lab/experiments/kernel-dsm-pause-exit.patch)，另行构建 `-sshpool-gvm-pf14`。配置除 LOCALVERSION 外保持一致，零 fuzz 重放与实际编译源码逐字节一致。QEMU、客体内核和 initramfs 保持原哈希。

开关为 `kvm_intel.dsm_force_pause_exit=1`，默认关闭，只在研究内核的一次性引导项中显式启用。它仅针对 Intel VMX 路径中已启用 DSM、没有 PLE、且硬件允许 PAUSE 拦截的 VM，在实际进入客体前设置控制位。普通 VM 不进入这个分支；AMD SVM 和 ARM 不在本次范围内。默认构建和安装流程不自动启用该候选。

无 PLE 时，KVM 的 `vmx_vm_init` 会自动设置 `disabled_exits` 中的 PAUSE 位。这里的 **force** 明确覆盖 DSM VM 的该策略，包括用户空间请求的禁用策略，不能把它描述成完全透明的配置变化。退出处理使用实际 CPL；原来的 PLE 路径只可能来自内核态，显式拦截还可能来自用户态。四个客体 vCPU 各在 CPL 3 执行 64 次 PAUSE 后继续运行并校验结果。

PF12、PF13 的候选门控没有实际启用拦截，记录中的 PAUSE 退出为零，保留为未生效对照。仅看模块参数为 Y 不足以确认控制位已经生效；PF14 的验收要求实际 PAUSE 退出事件。

## 同一 PF14 内核的开关对照

两轮均为同一 QEMU、四 vCPU 客体、相同的一轮 32 个时钟样本与四个定时器，宿主均为 lazy 抢占。开关通过一次性重启切换，每次都核对实际参数；以下四份跟踪均无丢失。

| 开关 / 节点 | KVM 区间最大值 | 可运行等待最大值 | 宿主定时器间隔最大值 | PAUSE 退出次数 |
|---|---:|---:|---:|---:|
| 关闭 / 0 | 249.771 ms | 250.162 ms | 249.802 ms | 0 |
| 开启 / 0 | 0.125 ms | 63.965 ms | 63.120 ms | 306,400 |
| 关闭 / 1 | 243.494 ms | 216.053 ms | 243.514 ms | 0 |
| 开启 / 1 | 3.645 ms | 213.103 ms | 211.926 ms | 325,680 |

KVM 区间尾部明显缩短，但节点 1 的调度等待仍约 213 ms，没有同等改善。开启时每侧完整 KVM 区间数为 336,327/355,605，关闭为 39,916/40,901；更多退出有开销，不能把区间缩短直接解释为编译吞吐提升。PF11 的 7.98 秒属于另一次较长窗口的历史观察，不能替代这组同内核对照。

## 余下等待期间，CPU 在做什么

随后用 `check-timer-progress.py` 离线重算同一组完整跟踪，没有再次启动实验或更换内核。它逐 CPU 选取两个真实本地定时器入口之间的最长窗口，统计窗口内部的 KVM、调度和中断事件，同时给出相邻事件的最大间隔。数据沿用原始跟踪 SHA-256；不同 CPU 的事件不会填补本 CPU 的空档，采样边界不会被外推成定时器窗口。

| PAUSE 开启时的节点 / 宿主 CPU | 定时器入口间隔 | 内部 PAUSE 退出数 | 相邻已记录事件最大间隔 |
|---|---:|---:|---:|
| 0 / 0 | 54.600 ms | 6,300 | 0.020 ms |
| 0 / 1 | 63.120 ms | 8,793 | 0.010 ms |
| 1 / 0 | 211.926 ms | 28,961 | 0.295 ms |
| 1 / 1 | 206.802 ms | 28,197 | 0.025 ms |

节点 1 两个窗口相互重叠。CPU 0 的窗口在 `365.377704–365.589630` 秒，其内部唯一调度切换发生于 `365.589613` 秒，最后才调入此前等待约 213 ms 的 DSM 线程。CPU 1 的相应窗口没有调度切换。这说明两个 CPU 在定时器空档中持续运行 KVM 进入/退出路径，不能把这段等待解释成整个实验 VM 被 ESXi 持续停调。关闭 PAUSE 的对照中，每个最长窗口都只有一对 KVM 进入/退出，相邻事件最大间隔为约 219–250 ms。

这些记录仍不能确定宿主定时器为何没有及时到达，也不能仅凭 KVM 跟踪点的 `d..1.` 标志断言整个窗口持续关闭中断：该标志只描述采样位置。频繁 PAUSE 退出没有保证 DSM 工作线程及时运行；下一步需要单独验证中断交付与宿主调度机会，并保持原来的时钟、内存和关闭验收。不能把诊断中的退出次数当作有用计算或吞吐提升。

[补充数据](evidence/ssi-timer-progress-20261106.json) 保存全部四份跟踪的哈希、每 CPU 最长窗口、事件计数和边界事件。它是完整原始跟踪的分析摘要，不能独立重放所有内部事件；完整记录仍保留在私有实验目录。分析器的合成测试验证跨 CPU 隔离、窗口边界和拒绝条件，不冒充新增硬件实验。

## 采集与验收边界

采集器使用每宿主 CPU 64 MiB 缓冲、全局时钟、线程身份和启动 tick 校验，并记录单调时钟及 RAW 时钟心跳。导出复用 64 KiB 分块 JSON 写入，避免在 1 GiB 实验 VM 中复制整个大字符串。分析在管理机离线执行。

PF14 的三轮采集产生大量退出，两个节点分别只保留 2,971,553/4,584,722 和 2,996,942/4,444,928 个事件，均被拒绝用于时间分析。没有扩大实验 VM 的内存占用或放宽丢失检查；后续开关对照各采集一轮完整时钟探针。诊断窗口缩短不等于完整工作区验收减少轮数，无跟踪运行仍执行三轮，20 ms 定时器仍须低于 250 ms。

首次无跟踪运行在 SFTP banner exchange 阶段超时，时钟与 PAUSE 程序没有上传。虽然后续内存测试、另一次 SFTP 回取和关机成功，这一轮仍是不完整失败，证据单独保留。

重新一次性启动同一 PF14 后，无跟踪复测完成三轮、96 个时钟样本和 12 个定时器。其中一个请求 20 ms 的定时器耗时 **455.952457 ms**，违反原定 250 ms 上限；其余两轮通过时钟分析器。客体程序打印 `CLOCK_PASS` 仅证明它内部检查通过，不能替代外部延迟验收。**完整 SSI 工作区仍然失败，不能因跟踪窗口改善而宣布稳定性修复。**

完整工作区还必须通过 RTC、watchdog、时钟、内存、文件传输与关闭检查。PAUSE 拦截增加 VM 退出开销，单次窗口的最大值不等于吞吐提升，更不能当作任意程序获得多机总算力的证明。后续应先定位余下停顿、建连异常和关闭协议，再验收持久存储与业务容器。

## 复核

完整原始跟踪体积较大，保留在私有实验目录。公开 [实验数据](evidence/ssi-vcpu-residency-20261106.json) 保存其哈希、完整性计数、分析摘要、关键原始端点摘录、客体日志和恢复记录；端点摘录不能冒充全量重放。

```sh
python3 scripts/ssi-lab/check-vcpu-residency.py node0-trace.json
python3 scripts/ssi-lab/check-timer-progress.py node0-trace.json --limit 10
python3 -m unittest discover -s scripts/ssi-lab -p 'test_*residency*.py'
python3 -m unittest discover -s scripts/ssi-lab -p 'test_timer_progress.py'
```

实验结束后两台 VM 回到默认 Ubuntu，核对机器身份、`/lib -> usr/lib`、GRUB 环境、QEMU/DSM/跟踪残留和原防火墙；CPU 限额保持上轮已验证的 `-1`。构建用 Lima 关闭。业务主机、公司目录和生产隧道不参与实验。
