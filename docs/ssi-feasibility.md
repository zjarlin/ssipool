# 严格 SSI：目标、当前阻塞与实验验收

核查日期：2026-11-05。本文更新目标定义，不代表已经交付 SSI。SSHPool 的 Rust 入口运行时仍是普通 Ubuntu 工作台与用户态任务调度器；独立的 GiantVM 实验已经修改研究宿主内核并验证小工作集跨节点共享，实测范围见 [双节点实验](ssi-lab.md)。

2026-11-08 的 [PF30 写授权实验](ssi-write-grant.md) 已把数百次重复缺页绑定到同一次写指令调用，并测试默认关闭、最长 1 ms 的授权保留候选。最小样本有改善，完整客体的原 250 ms 门槛、跟踪归因失败与取消/公平性限制继续保留；这不改变下列严格 SSI 目标或默认产品准入。

2026-11-09 的 [原子操作实验](ssi-atomic-grant.md) 补充了同一 ESXi 上四轮双端 LOCK XADD 的计数完整性与有限进展证据；另一次启动连接超时保留为失败，任意负载公平性仍未证明。下列跨物理资源与有状态恢复目标不变。

## 本轮明确的硬目标

一个 Linux 客体操作系统直接使用多台物理设备的 CPU、内存和磁盘。现有 Docker 镜像中的 sub2api、PostgreSQL、Redis 及编译工具无需按任务重写或重新提交，单个服务实例可以使用超过任一节点的资源。正常运行时，主要计算和磁盘 I/O 离开入口设备；主要计算节点失效后，其余设备恢复服务。

SSH 作业调度、sccache、NFS、数据库主备和容器多副本都不能单独验收上述目标。它们可以作为独立能力交付，不能折算为严格 SSI 的完成百分比。

## 已核查的可复用基础

### GiantVM：最接近未修改客体与应用的路线

[GVM-kernel](https://github.com/GiantVM/GVM-kernel) 和 [GVM-qemu](https://github.com/GiantVM/GVM-qemu) 的新仓库明确描述多台物理机组成一个虚拟机，客体 OS 与用户态程序不需修改，`main` 路线使用 TCP DSM。不能只依据旧 Linux 4.x/QEMU 2.x 仓库断言项目没有新进展。

本次读取的版本与配对要求：

| 组件 | 核查版本 |
| --- | --- |
| GVM-qemu `main` | `da3f3b05d23ba714a3e961f80c059c376007d7d7`，QEMU 10.1.2 |
| GVM-kernel `upstream/7.1-rc3` | `6317a6badf4f5a42e8ff7f6881b3a9199e6c0b54` |
| GVM-kernel `main` | `46e1874790e0eceb59c3386bca027a8a743bb2db`，不是该 QEMU README 指定的 TCP 配对分支 |

QEMU README 要求 TCP 版本配合 `upstream/7.1-rc3`，开启 `CONFIG_KVM_DSM_IRQ_FORWARD` 与 `CONFIG_KVM_DSM`。它列出的 KVM 能力号和退出原因必须两边一致，仅版本字符串相同不能证明 ABI 一致。共享内存分支使用不同 ABI，不能直接混配。

公开安装路径编译 `x86_64-softmmu` 并启用 KVM，需要运行定制宿主内核。内核 README 将 ARM 支持标为开发中；这是作者的开发状态陈述，不是本项目验证过的支持矩阵。即使以后支持 ARM，也不能据此推导 ARM 与 x86 可以同时承载同一个未修改客体地址空间。

尚无本项目实验证据支持：现有 Apple Silicon + x86 组合、未修改的业务镜像、数据库 ACID、失节点内存恢复、网络分区容错或接近各机器性能之和。源码涉及内核和 QEMU 各自许可证，不因本控制器采用 MIT 而变成 MIT。

### Popcorn：需要配套编译器的另一条路线

[popcorn-compiler](https://github.com/ssrg-vt/popcorn-compiler) README 说明需要多 ISA 代码生成、迁移点、栈状态转换、代码和数据布局对齐；公开限制包括 C 应用及不支持内联汇编。它不能直接让既有 Go 服务、任意容器机器码和 PostgreSQL/Redis 组合获得透明迁移。不能把上游某个默认分支的日期当作整个研究方向的维护结论。

## 当前设备的实际阻塞

只读检查使用系统架构、`/dev/kvm`、CPU 虚拟化标记和 `systemd-detect-virt`，未加载模块、重启宿主或改生产数据。

- x86 Linux Worker 是 VMware 客户机；`/dev/kvm` 不存在，CPU 未暴露 `vmx` 或 `svm`。普通 Docker 可用不代表可以运行嵌套 KVM。是否能开启需由上层 VMware 配置确认，不能由本程序绕过。
- Apple Silicon 上的工作台是 aarch64 Linux，当前同样没有 `/dev/kvm`。macOS 自身的虚拟化框架不能直接替代 GiantVM 的 Linux KVM DSM 补丁。
- 另一台 Mac 的运维 SSH 终点是 Darwin/ARM64，Docker Linux VM 的存在不等于已经安装 GiantVM 内核或支持嵌套虚拟化。

本轮已在用户授权的 ESXi 上新建两个 x86_64 实验 VM，实际启动定制宿主内核，并确认两节点 DSM capability 249 为 1、KVM 创建 VM 成功；原有业务 VM 未改动。实验中发现并处理 QEMU 单节点空指针与内核页引用生命周期问题，详细结果见 [双节点实验记录](ssi-lab.md)。这两个节点位于同一物理宿主，不能记成两台物理机资源汇聚；Apple Silicon 混合执行、业务容器及故障恢复也仍未验证。

## 容量、性能和故障不能混为一个指标

正常情况下汇聚容量可以研究，性能是否接近相加必须按相同工作负载测量。不同型号 CPU 的逻辑核数不能当作等价算力相加；网络带宽、远端缺页、缓存一致性、锁竞争和数据库提交延迟可能使性能明显低于预期。

设各节点可供集群使用的内存为 `R_i`，某个节点 `k` 故障后，物理存活容量上界为 `sum(R_i) - R_k`，还必须扣除系统、复制和恢复开销。这是容量上界，不是已经实现的分配器。为了单节点故障时恢复所有已承诺工作集，接纳量应受最坏存活集合约束；并不一定要求节点等量，也不存在固定三台就足够的规则。

现场读到的主节点总内存约 98 GiB，两个 Mac 宿主合计 64 GiB；这些是总容量，不是可立即使用的余量，且部分 Mac 内存已经给虚拟机分配，不能重复计算。失去主节点时，剩余设备不可能仍提供约 162 GiB 物理内存。远程 swap、压缩或磁盘映射不能当作同等速度和容量的 DRAM。

聚合本身不提供容错。唯一内存页随节点失去而丢失时，客体可能崩溃；要恢复还需检查点、复制及设备状态一致性。数据库需要明确的持久化确认、写入隔离和恢复协议。常驻副本也会占用后备设备的资源，不能同时承诺后备零资源开销和无恢复成本。

## 分阶段实验门槛

1. 独立实验环境有至少两个同 ISA、支持 KVM 的节点，实际加载匹配的 GVM 内核/QEMU；这一条件对应已核查的上游路线，不声称所有可能的 SSI 都只能同 ISA。
2. 同一个客体 Linux 启动；同一多线程进程在两台物理机都产生可核验的执行负载。超过单节点配额的随机写读内存测试通过，排除 swap、单节点超配和只伪造拓扑。
3. 原镜像固定到 digest，Docker/OCI 与 PostgreSQL 多进程共享内存、锁、信号、Redis 持久化、sub2api 应用检查通过。
4. 磁盘随机 I/O、`fsync` 与断电恢复有真实数据校验，不能把远端文件系统挂载当成完整分布式块设备容错。
5. 节点崩溃及网络分区时只保留一个有效写入方；已确认事务、恢复点、恢复时间、失效内存页恢复方式与剩余容量全部可测。
6. 用隔离的演示数据完成迁移、恢复和切回演练，再针对指定生产版本制定变更；尚未通过实验门槛时不迁移生产数据库。

对应 Gherkin 规格在 `features/110-pooled-linux.feature` 和 `features/120-stateful-recovery.feature`。均为未完成目标，不是可用运行时或自动执行过的测试。

## 对已有其他 feature 的影响

原有 SSH、作业、归档和沙箱的已验证证据仍然有效，但只属于任务调度器。在线节点管理、持久队列、sccache、分布式编译等不满足本轮严格 SSI 定义，不能以这些功能代替该目标。生产多实例、数据库分片/主备也是独立架构选择，需要用户接受应用层拆分与性能/容量边界后才能进入部署。
