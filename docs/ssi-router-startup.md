# 路由版本在启动阶段拒绝

2026-11-08。协议 5 候选把固定长度的 HELLO/ACK 放到路由初始化阶段。与协议 3、4 混配时，新节点均在首次 `KVM_RUN` 前明确失败退出；旧主节点仍可能先执行客体，并可能需要外部清理。这轮直接调用 QEMU 的实验未满足完整启动前拒绝场景。后续 [双端封存启动器](ssi-launch.md) 已通过四种混配验证并将该场景升级为 verified；本页旧主节点已经执行的失败结论不变。

本轮仅使用同一 ESXi 上的两个专用 PF24 VM，不挂磁盘或业务目录。原始 ioctl、进程退出、错误、宿主日志和工作区回归见 [证据](evidence/ssi-router-startup-20261108.json)。

## 协议改动

在 `qemu-clock-resume.patch` 后应用 `experiments/qemu-router-startup.patch`，版本从 4 升至 5。固定前缀先检查 magic，再检查版本，然后读取节点、目标节点、节点数及 CPU 拓扑。这样不必先等待旧版本可能永远不会发送的可变长时钟报文。

全部出站确认和入站 HELLO 到齐后才发布 `SSI_ROUTER_READY`。接收握手在独立线程进行，避免初始化阶段尚未进入主循环时双向等待。监听器接齐本轮连接后关闭，启动线程回收监听线程；初版常驻监听线程的两次混配记录另行保留，没有把它作为最终候选。

连接、握手读写和等待受 15 秒看门狗约束，协议错误使用失败退出，避免等待持有 BQL 的正常退出回调。该路径不承诺设备刷盘或数据库一致性。本轮没有单独验证静默对端、失联、多于两个节点、RDMA、重连或拓扑错误注入。

最终二进制 SHA-256：`f0804eac45a00ccdd1c826298e205cfcc4530fcaa14674cf52688c8be408cb98`。补丁从上一候选源码零 fuzz 重放，与实际编译文件逐字节一致；编译日志、前后源码哈希和补丁哈希随证据保存。补丁为 GPL-2.0-or-later，不进入默认构建或生产部署。

## 真实混配结果

探针不带 `-S`，用原生 `strace -f` 跟踪 QEMU 的 `execve`、线程创建、KVM ioctl 和退出。以下数字为首次调用入口计数，包含未返回的 `KVM_RUN`；恢复记录不重复计数。

| 节点 0 / 节点 1 协议 | KVM_RUN 次数 | 退出与清理 | 完整启动前拒绝 |
| --- | --- | --- | --- |
| 5 / 4 | 0 / 0 | 双方自行退出 1 | 本次通过 |
| 4 / 5 | 873 / 0 | 新节点自行退出 1；旧节点 35 秒后 SIGTERM 清理 | 失败 |
| 5 / 3 | 0 / 0 | 双方自行退出 1 | 本次通过 |
| 3 / 5 | 4 / 0 | 双方自行退出 1 | 失败 |

初版候选的 4/5 方向也记录到旧主节点执行 164 次 `KVM_RUN`。最终候选的旧主节点虽然最后退出码也是 1，仍明确记录 `forced_cleanup=["SIGTERM"]`，没有原生退出观察时间；退出码不能把它改写成协议自行拒绝。

新节点无法撤销旧主节点已经执行的指令。这暴露了启动器必须在执行任何 QEMU 前完成双方准入，并将核验对象与实际执行字节绑定的需求。后续 `ssi-launch` 已实现并实测这一边界；本页实验脚本的事前哈希检查不构成双端准入，后续启动器的许可发送也不是原子事务。

## 工作区回归

单节点和双节点均使用同一个最终候选，沿用原 250 ms 定时器上限、四 CPU 共享内存校验和 1 MiB SFTP 往返。单节点完整通过。首轮双节点的 SSH、三轮时钟探针、共享内存和暂停程序通过，但 SFTP 在 SSH banner 阶段超时，因此完整回归失败；随后客体关机、双向路由排空及两个 QEMU 退出 0 均有记录。

这轮双节点最大定时器样本为 27,645,284 ns，低于原门槛，但启动仍丢失 RTC 中断；宿主关闭时仍记录 DSM `-104`，不能把路由排空视为整个内核的正常关闭。

针对 SFTP 失败补跑的上一版基线和同一候选均完成全部操作，耗时分别为 85.17 秒、88.91 秒；候选复测最大定时器样本为 32,965,701 ns，启动检查通过。所有记录均保留。单次成功不覆盖已有失败，不据此声称长期稳定或已定位网络问题。

## 检查与复现

两台实验 VM 均须先核验归属、PF24 内核、三个镜像哈希、实验端口全部 TCP 状态和防火墙。使用 `probe-router-startup.py --help` 查看参数；两侧分别指定实际运行的候选或旧版二进制，并使用独立输出目录。探针只清理本次创建的进程组，任何强制清理都保存为失败。

`check-router-startup.py` 接受证据中的单个 `runs[]` 对象。它要求真实 `execve` 与启动参数一致、KVM VM 创建成功、完整线程创建与退出，以及非空 ioctl 跟踪。它重算执行次数，不信任汇总中的零，也不允许通过 `-S` 把未执行伪装为拒绝。

```sh
jq '.runs[0]' docs/evidence/ssi-router-startup-20261108.json > /tmp/router-startup-row.json
python3 scripts/ssi-lab/check-router-startup.py /tmp/router-startup-row.json \
  --require-both-before-guest
python3 -m unittest discover -s scripts/ssi-lab -p 'test_router_startup.py'
```

严格选项在旧主节点已执行的记录上失败；超时清理记录连普通完整采集检查也不能通过。测试同时覆盖缺失日志、缺失线程退出、伪造计数、暂停参数及错误内核拒绝。普通 CI 只重放这些检查，不伪装具备研究内核。

实验结束后两台 VM 恢复原版内核，核对原引导文件哈希、`/lib -> usr/lib`、空 GRUB 待执行项、无实验进程和原防火墙。DHCP 地址变化通过 ESXi 控制面发现，再以原 SSH 主机密钥和 machine-id 核实；没有重置 VM。临时通信规则在恢复前删除。
