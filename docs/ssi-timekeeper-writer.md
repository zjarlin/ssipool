# PF29 timekeeper 写入者与重复缺页

本轮把已观察到的长时间读取进一步定位到实际序列写入临界区。正式采集脚本复跑时，一次奇数序列持续区间达到 **952.614 ms**，其中更新阶段 264.033 ms、发布阶段 688.581 ms；最大应用等待 **491.636 ms**。这增加了可重放的诊断能力，**没有提交或证明运行时修复**，原 250 ms 门槛不变。

## 完整采集结果

两台 VM 仍位于同一物理 ESXi。宿主 PF29、QEMU、原版 Ubuntu 6.8 客体、initramfs 与应用探针哈希均固定；每个客体运行六次时钟探针，共 24 个应用定时器。全部原始客体跟踪随[证据清单](evidence/ssi-timekeeper-writer-20261108.json)提交。

| 运行 | 测量窗口内完整写入次数 | 最大写入区间 | 最大应用等待 | 宿主跟踪范围 |
| --- | ---: | ---: | ---: | --- |
| control-a | 389 | 0.005 ms | 20.339 ms | 无 |
| pair-a | 4,736 | 740.969 ms | 164.449 ms | 无 |
| pair-b | 6,729 | 870.864 ms | 1,298.593 ms | 仅第一轮：KVM、调度、中断、缺页 |
| pair-c | 4,328 | 451.228 ms | 314.041 ms | 全六轮：仅静态缺页事件 |
| control-d | 467 | 0.019 ms | 20.225 ms | 无，使用正式采集脚本 |
| pair-d | 4,590 | 952.614 ms | 491.636 ms | 无，使用同一正式采集脚本 |

pair-a 的有限应用采样通过，不抵消 pair-b/c/d 及此前的失败。长写入区间也不等于某个应用定时器的等待：pair-a 的最长读调用 806.300 ms，pair-d 的最长读调用 964.617 ms。报告只按同一客体 ftrace 时间域列出实际相交的读写区间，不把应用单调时钟直接减去跟踪时间。

所有运行完成身份核对、计时、内存压力、用户态暂停与 SFTP 数据校验；QEMU 单端退出 `[0]`、双端退出 `[0,0]`，双端 QUIESCE/DRAIN 与内核关闭代际完成。双节点串口仍有 `workqueue ... hogged CPU` 告警，完整日志保留，正常关闭不覆盖这些问题。

## 写入阶段的边界

采集入口仍是 [trace-guest-timers.sh](../scripts/ssi-lab/trace-guest-timers.sh)，新模式 `writer` 在既有 `ktime` 模式上增加三处指令探针。仅适用于证据固定的 ELF，必须核对符号地址与外层运行器的二进制 SHA-256。

| 事件 | `timekeeping_advance` 偏移 | 固定指令地址 | 含义 |
| --- | --- | --- | --- |
| `tk_write_begin` | `+0x2e3` | `ffffffff81212d13` | 奇数序列递增之后 |
| `tk_update_done` | `+0x2f2` | `ffffffff81212d22` | `timekeeping_update` 返回之后 |
| `tk_write_end` | `+0x30f` | `ffffffff81212d3f` | 发布并递增为偶数之后 |

三处读取 `tk_core` 的 u32 序列，固定地址 `ffffffff8401b4c0`。`timekeeping_advance` 是 `ffffffff81212a30`。第一处之前的递增在 `81212d0c`；第二、三处之间包含 `81212d35` 的 `rep movsq`，复制 280 字节，再于 `81212d38` 递增为偶数。三处均仍持有 timekeeper 写锁。完整反汇编在证据中保存。

检查器 [check-guest-irq.py](../scripts/ssi-lab/check-guest-irq.py) 复用既有计数、停止栅栏、逐 CPU 零丢失和函数边界检查。新增规则要求同 CPU/PID 的完整写入有且只有一个更新阶段，序列始终为同一奇数，再变为下一偶数，允许 u32 回绕，拒绝重叠临界区。所有三种探针的命中数必须精确等于事件数。

测量标记前后的启停过程会逐个切换探针，不完整记录不补造耗时。与测量窗口相交的完整调用必须通过阶段校验；跨越标记的调用可以解释阶段归属与重叠，但不进入窗口内耗时分布。内部孤立入口、返回或更新仍然拒绝。测试覆盖计数吻合但阶段缺失、身份错误、重复阶段、错误序列、回绕及跨标记调用。

这些是探针间的墙钟区间，包含执行、页访问、宿主调度和探针本身的开销，不是纯 CPU 时间。探针读取共享页也可能改变 DSM 页竞争；单节点对照不能排除双节点的观测扰动。

## 全窗口的重复缺页

pair-c 两端只启用宿主静态 `kvm_page_fault`，覆盖全部六轮时钟试验。原始记录分别有 **77,550 / 73,415** 个事件，逐 CPU 计数一致且无丢失；两份完整压缩 JSON 随仓库提交，并由 [check-timekeeper-faults.py](../scripts/ssi-lab/check-timekeeper-faults.py) 重放。

固定客体的 `tk_core` 与 `shadow_timekeeper` 共用 GFN `0x401b`。同一 vCPU 连续出现相同 RIP、地址和错误码的部分序列：

| 节点 / vCPU | 指令 | 地址 | 次数 | 第一至最后一次缺页跨度 |
| --- | --- | --- | ---: | ---: |
| 0 / 0 | `81212d35`，发布复制 | `0x401b4c8` | 41 | 313.402 ms |
| 0 / 0 | 同一指令和地址，另一序列 | `0x401b4c8` | 28 | 280.089 ms |
| 1 / 2 | `81211634`，更新写入 | `0x401b458` | 59 | 442.206 ms |

这些写缺页的错误码都是 `0xdea`；读序列指令也有重复缺页。检查器按目标线程逐条处理完整事件流，任何不同 RIP、地址或错误码都截断序列；不能先过滤目标页面再把不相邻记录拼在一起。线程集合、PID 启动时间、vCPU 编号、事件类型、全局时钟和缓冲区计数均需通过验证。

**跨度不是单次缺页服务耗时，也不能证明这些记录属于同一次函数调用或指令完全没有前进。** 两端宿主与客体时钟没有建立直接对齐，报告不做跨域减法。pair-b 的高密度宿主跟踪只覆盖第一轮，当轮最大应用等待 30.527 ms；后五轮才出现最大 1,298.593 ms。那两份私有原始记录已保留哈希和采集范围，但不宣称在 CI 全量重放，也不能用它排除后五轮的宿主原因。

PF29 源码中 `dsm_handle_read_req` 在 owner 分支会把页面改为共享并撤销写权限，读请求也迁移 owner；写缺页完成后映射可写，但映射锁不覆盖随后客体指令的执行。它与重复写缺页共同提示下一步检查“授予可写映射后、指令推进前是否再次被撤销”。目前没有记录每次授予、撤销与指令推进的共同身份，仍是待证实假设。任何后续限期保留写权限的实验都需要另行验证锁顺序、关闭中断、读写公平性和数据一致性，不能仅靠增加等待或延长超时称作修复。

## 复现与恢复

```sh
sh /tmp/trace-guest-timers.sh start writer
# 运行六轮带 TIMER_INTERVAL 的既有时钟探针，再收集完整归档。
sh /tmp/trace-guest-timers.sh stop
python3 scripts/ssi-lab/check-guest-irq.py capture.tar.gz clock.log
python3 scripts/ssi-lab/check-timekeeper-faults.py host-faults.json.gz
python3 -m unittest discover -s scripts/ssi-lab -p 'test_timekeeper_writer.py'
```

客体 CLI 会先输出分析，再按原 250 ms 门槛决定退出状态。归档中的实际运行器、采集器源码、全部应用日志与内存/文件传输结果可供核对；旧证据保持原样。

实验后两台 VM 已恢复 `6.8.0-147-generic`，核对机器身份、原启动文件哈希、原 GRUB、防火墙、实验进程、跟踪实例和 TCP 状态，移除本轮一次性 GRUB 入口并保留研究内核产物。Lima 构建机保持运行。跨物理机容量、异构 ISA、持久存储、业务容器/数据库和失节点恢复仍未验收。
