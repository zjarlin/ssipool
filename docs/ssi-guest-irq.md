# PF29 客体中断函数与时间读取分段

后续[写入者观测](ssi-timekeeper-writer.md)已加入独立的 `writer` 模式，记录实际奇数序列临界区与全窗口宿主重复缺页。本页记录及历史证据保留原结论。

2026-11-08，在同一物理 ESXi 的两个独占实验 VM 上继续定位计时停顿。PF29 与固定的 PF29-close QEMU 保持不变，本轮修正的是采集边界与可重放检查，**没有提交新的运行时修复**。双节点仍出现 323.480 ms 与 553.933 ms 应用等待，超过原 250 ms 门槛。

## 已观察到的慢路径

| 采集 | 完整事件 | 最大应用等待 | 最大时间读取调用 | 归因记录 |
| --- | ---: | ---: | ---: | --- |
| control-b，三个函数入口/返回 | 12,140 | 20.329 ms | 0.014 ms | 完整 |
| pair-b，相同函数集合 | 201,396 | 323.480 ms | 662.613 ms | 完整，计时失败 |
| control-c，增加时间读取分段 | 17,458 | 20.293 ms | 0.021 ms | 完整 |
| pair-c，相同分段集合 | 219,942 | 553.933 ms | 467.787 ms | 完整，计时失败 |
| control-d，正式采集脚本 | 16,698 | 20.280 ms | 0.041 ms | 完整 |
| pair-e，正式采集脚本 | 288,734 | 259.455 ms | 523.303 ms | 完整，计时失败 |

三个函数为 `ktime_get_update_offsets_now`、`tick_sched_do_timer`、`tick_sched_handle`。pair-b 的后两者最大墙钟区间分别为 663.875 ms 与 726.789 ms。最大函数区间不一定属于最大应用等待，不能相互替代。

pair-b 中一次 166.750 ms 应用等待的到期中断为 124.946 ms，其中时间读取调用占 121.257 ms；另一次 177.894 ms 等待的中断为 150.031 ms，主要区间在应用唤醒回调内，时间读取只有 1 μs。最长 323.480 ms 应用等待的到期中断反而只有 7.104 ms。剩余停顿存在多个位置。

pair-c 的最长时间读取调用在 CPU 3，从 ftrace `86.318945` 秒到 `86.786732` 秒，共 467.787 ms，只有一次完整读取尝试：

| 区间 | 耗时 |
| --- | ---: |
| 函数入口至首次观察到偶数序列 | 467.776 ms |
| 偶数序列至时钟源返回（含指针加载） | 5 μs |
| 返回后的数据计算至最终序列检查 | 3 μs |
| 序列检查至函数返回 | 3 μs |

最终 `before=after=43752`，这次没有重试。第一段包含函数前序、页面访问、奇数序列等待、可能的宿主停调及探针开销，**不是已测得的纯自旋时间**。本轮没有记录序列写入者临界区或同期宿主调度，不能据此确定 DSM 页锁、写入者或 ESXi 中哪一个导致长等待。

pair-c 最大应用等待 553.933 ms 的到期中断只有 16.012 ms，上述最长函数调用不在该中断内。应用单调时钟与 ftrace 时间仍分开处理，禁止跨时间域相减。跟踪本身也可能改变 DSM 页竞争，单节点对照不能证明双节点跟踪开销可忽略。

正式脚本复跑 pair-e 又捕获到一次 523.303 ms 调用：首次序列检查由 `39158` 变成奇数 `39159`，随后经过 520.256 ms 才在下一次尝试读到偶数 `39160`，最终复核相等并返回。这是实际发生序列变化和重试的证据；等待区间仍包含页访问和宿主执行机会，不能把整段解释成连续执行 PAUSE。该轮最大应用等待为 259.455 ms，仍超过原门槛。

## 采集边界为何需要修正

旧 pair-a 没有报告 kprobe missed，但 `tick_sched_do_timer_enter` 命中 17,431、缓冲区只有 17,429 条；函数归因被拒绝。仅先禁用 trace event 再冻结缓冲区仍有竞态：清除事件记录标志与真正停用探针并非一个动作，探针命中计数仍可能增长。该失败原始归档与脚本保留在本轮证据中；之前 PF28 的漏采证据也保持原样。

新采集只在独占、无磁盘、四 CPU 的实验客体运行，要求初始 trace instance、kprobe events 和全局 kprobe list 都为空。结束标记后先将客体 `/sys/kernel/debug/kprobes/enabled` 置零，等待同步，再冻结缓冲区和导出。删除本次探针并确认列表为空后恢复开关为一。该操作不作用于宿主，也不适用于共享客体。

检查器要求所有入口和分段命中数精确等于事件数、全部 missed 为零、逐 CPU 无缓冲区丢失。完整调用按同 CPU/PID 配对；孤立返回必须早于开始标记，未完成入口必须晚于结束标记。返回计数的额外命中只能由这些末尾调用解释，不补造持续时间。分段必须严格按“偶数序列、时钟返回、序列复核”出现，初始序列相同且为偶数，仅序列变化允许重试，最后一次必须相等。

## 复现与限制

先看 [采集入口](../scripts/ssi-lab/trace-guest-timers.sh)，再看 [函数检查器](../scripts/ssi-lab/check-guest-irq.py)。它复用已有定时器解析与关联逻辑，通过显式事件集合扩展，不修改模块全局集合。默认 `timers` 模式保留 tracepoint 用法；`irq` 添加三个函数，`ktime` 再添加分段。

```sh
sh /tmp/trace-guest-timers.sh start ktime
for trial in 1 2 3 4 5 6; do
  sh -c 'echo TRACE_CLOCK_PID=$$; exec /tmp/ssi-clock --timer-intervals' || exit $?
done
sh /tmp/trace-guest-timers.sh stop
```

分段偏移只适用于证据中哈希固定的原版 Ubuntu `6.8.0-147-generic` 客体 ELF，并要求 `nokaslr`。`+0x38` 在初始奇偶循环之后，`+0x4e` 在时钟源调用返回处，`+0xda` 在最终序列比较处；不在 PAUSE 循环逐次打点。外层运行器在启动前核对两端内核、QEMU、客体内核与 initramfs 的 SHA-256，采集器另外核对符号地址；仅版本名相同不足以换用这些偏移。

保存应用日志并取回 `/tmp/ssi-timer-capture` 的完整归档后：

```sh
python3 scripts/ssi-lab/check-guest-irq.py capture.tar.gz clock.log
python3 -m unittest discover -s scripts/ssi-lab -p 'test_guest_irq.py'
```

即使完整性全部通过，应用等待超过 250 ms 时 CLI 仍在输出 JSON 后退出一。证据保留所有应用区间、完整压缩跟踪、探针源文件、反汇编、运行时哈希、工作负载与关闭日志，不只保留选中的慢片段。

[证据清单](evidence/ssi-guest-irq-20261108.json) 还保留正式脚本复跑 pair-d 的 SSH banner 超时：它未开始采集，也没有完成计时、内存和文件传输回归，不能因两端正常退出就算通过。正式采集脚本由 control-d 和后续 pair-e 验证；二者使用相同源文件。

实验后两台 VM 恢复 stock 内核，核对原 GRUB、启动文件哈希、防火墙、进程、跟踪与 TCP 清理。跨物理机资源汇聚、异构 ISA、持久存储、业务容器和失节点恢复仍未完成；本轮观测不提升这些目标的状态。
