# 显式软件 TSC 缩放实验

2026-11-09，独立 ESXi 上的专用 Linux VM 完成 PF31/PF32 单 vCPU 对照。**PF32 在原生、升频、降频和另一物理节点的目标频率下，同时通过 RDTSC、RDTSCP、TSC MSR 与 pvclock 的短窗口验收。** PF31 的 MSR 失败保留。默认运行时没有启用软件缩放，`ssi-preflight` 的不同原生频率拒绝继续生效。

这一步只证明隔离探针的比例换算。后续[双 vCPU 交替执行实验](ssi-tsc-multivcpu.md)通过了最后一组速率检查，但尚未确认预设对齐界限。没有运行跨物理的同一 Linux 客体，没有验证并发多 vCPU、定时器、暂停恢复、长期漂移、存储或数据库接管，不能称为完整时间虚拟化或严格 SSI。

## 实现与失败修复

按顺序在 PF30 上应用：

1. `scripts/ssi-lab/experiments/kernel-software-tsc.patch`，构建 `7.1.0-rc3-sshpool-gvm-pf31`。
2. `scripts/ssi-lab/experiments/kernel-software-tsc-msr.patch`，构建 `7.1.0-rc3-sshpool-gvm-pf32`。

两份 Linux 补丁沿用 GPL-2.0-only，不进入默认构建。PF31 通过默认关闭的 `kvm_intel.lab_tsc_scaling` 和逐 vCPU 实验属性 `KVM_VCPU_TSC_LAB_SOFTWARE` 显式选择。只有未执行、没有 catch-up、原生频率、稳定 TSC 的实例可以选择；运行后禁止改变比例或选择。内层嵌套必须关闭，存在硬件缩放时拒绝开放该实验。`KVM_CAP_TSC_CONTROL` 仍报告真实硬件能力 **0**。

软件路径复用 KVM 的 multiplier、offset 和 pvclock 换算，令 RDTSC/RDTSCP 退出到 KVM。首次 PF31 实测发现：默认 VMX MSR 位图让 `MSR_IA32_TSC` 直接在硬件读取，没有经过已有换算函数。因此两条指令和 pvclock 看似正确，MSR 仍按原生速率增长，零点还发生明显错位或无符号回绕。

PF32 对选中的 vCPU 额外拦截 TSC MSR 读取，转入已有公共换算路径；未选中的实例保留原路径。两个内核的精确源码、配置、镜像摘要和同一探针的反汇编一起归档，失败没有用新二进制冒充旧身份。

## 测量方法和结果

探针从原频率探针应用 `probe-tsc-scaling.patch` 得到；采集器应用 `capture-tsc-scaling.patch`。基线文件不改动。每组创建新的 KVM 实例，使用两个许可 CPU 分离观测线程和 vCPU，设置比例后再用 MSR 建立零点。实模式 CPL0 小程序在一次 `KVM_RUN` 中，以共享内存握手采集 12 组读数，最后 HLT。

每组顺序读取 RDTSC、RDTSCP、TSC MSR，记录 AUX 和 pvclock 的偶数版本。宿主 `CLOCK_MONOTONIC_RAW` 的前后读数包住整个客体采样。检查器固定排除第一个初始化区间，检查每个相邻区间和 1→11 总区间；所有速率包络必须完整位于预设千分之一容差内，三条 TSC 路径还必须有一致的零点和读取顺序。非原生软件频率必须排除原生速率，不能只相信 SET/GET。

PF32 显式软件模式的总区间如下，kHz 向外取整至 0.001：

| 请求 kHz | RDTSC 包络 | RDTSCP 包络 | TSC MSR 包络 | pvclock 速率包络 |
| ---: | --- | --- | --- | --- |
| 原生 2,095,148 | [2,095,066.485, 2,095,229.752] | [2,095,066.377, 2,095,229.644] | [2,095,066.210, 2,095,229.476] | [0.999961093, 1.000039019] |
| 升频 2,514,177 | [2,514,075.248, 2,514,274.665] | [2,514,074.316, 2,514,273.734] | [2,514,074.001, 2,514,273.418] | [0.999959926, 1.000039244] |
| 降频 1,676,118 | [1,676,052.625, 1,676,183.539] | [1,676,052.199, 1,676,183.112] | [1,676,052.163, 1,676,183.077] | [0.999961592, 1.000039698] |
| 目标 2,394,374 | [2,394,280.562, 2,394,468.211] | [2,394,281.454, 2,394,469.103] | [2,394,280.749, 2,394,468.399] | [0.999961393, 1.000039765] |

目标来自原物理节点的真实预检，原生值来自本候选已冻结的频率证据；清单通过摘要引用这两个来源。相同 VM 的 machine-id/DMI 摘要一致，四次采集使用四个不同 boot-id，避免拼接其他节点或陈旧启动数据。

两个版本各运行关闭/开启宿主开关两组矩阵，共 26 次探针调用：20 次正常 HLT、4 次降频设置拒绝、2 次软件属性不可用。其中 PF31 开启后 3 次非原生软件运行虽正常退出，仍被检查器判为 MSR 不一致，不能计为通过。所有捕获的前后状态一致、没有遗留实验进程或 KVM fd，日志增量仅包含预期降频拒绝。

关闭开关时软件属性不可用且未执行客体。开启开关但未选择的实例仍测得原生速率，运行后选择返回 EBUSY。选中实例的无效值/flags 被拒绝；正常运行后的改频返回 EINVAL，重新选择返回 EBUSY，频率读回不变。AUX 恒为预设值。代码保留 CR4.TSD/CPL 和 RDTSCP 可用性判断，但本轮没有验证 CPL3 权限异常或完整 CPUID 组合。

宿主的 MONOTONIC_RAW 仍由其 TSC 支撑，因此这里衡量的是嵌套客体相对 Linux 宿主的比例；没有独立外部 UTC 参考。拦截引入的开销没有作为性能结论验收。

## 证据、复现和恢复

先阅读本文，再运行 [检查器](../scripts/ssi-lab/check-tsc-scaling.py)，需要扩展采样时再修改两份探针/采集补丁。[清单](evidence/ssi-tsc-scaling-20261109.json)引用五份压缩归档：四次完整矩阵与实际编译源码。普通 CI 重放原始数据和反例，Linux CI 另行应用补丁、编译探针并验证错误内核拒绝，不启动实验 VM。

```sh
python3 scripts/ssi-lab/check-tsc-scaling.py docs/evidence/ssi-tsc-scaling-20261109.json
python3 -m unittest discover -s scripts/ssi-lab -p 'test_tsc_scaling.py'
```

实验只在专用 VM 使用一次性 GRUB 入口，宿主开关关闭组不传 `lab_tsc_scaling`，开启组传 `kvm_intel.lab_tsc_scaling=1`；两组均设 `kvm_intel.nested=0`，沿用 APICv 关闭和既有 PAUSE 实验设置。KVM 内建到内核，不能在正在运行的实例中切换宿主开关。

完成后已回到原版 `6.8.0-147-generic`，归档并移除本轮 PF31/PF32 启动项、内核、模块和远端探针。GRUB 配置、历史启动文件、防火墙和 Netplan 与实验前逐摘要一致。为安装腾出的 90 个 apt 下载缓存文件共 90,865,762 字节已从核对过的私有备份恢复，恢复后再次逐文件核对。VM 保持开机，Lima 构建实例没有停止。

双 vCPU 后续实验已保留三组完整矩阵：最后一组全部速率通过，偏移对照检出，但共同偏移配置的测量区间仍未完全落入 ±100 微秒门槛。下一步需先完成偏移对齐验收，再验证并发、定时器与暂停恢复并连接真实双端运行时。必须保留不同频率的默认拒绝，直到这些运行边界有实测证据。
