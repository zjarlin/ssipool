# PF18 / PF19：内核 DSM 入站流排空

2026-11-06。这一轮为真实 KVM 的单条入站连接增加排空屏障。确认只能在此前请求完成响应、释放页锁和 KVM SRCU 后发送。**整个分布式 VM 的正常关闭仍未完成，现有 QEMU 也没有自动发送这个新内核标记。** Ceph、持久磁盘、Docker、PostgreSQL、Redis 和 sub2api 均未接入。

实验只使用两个专用 x86 VM；它们仍位于同一台物理 ESXi。直接接口实验分别在每台 VM 上创建真实 KVM 实例，协议对端由探针模拟；工作区回归则由两台 VM 上的真实 QEMU 共同运行一个无磁盘 Linux 客体。这些记录不能证明跨物理机容量相加或故障接管。

## 接收标记不等于请求完成

一条 DSM 连接有八个处理线程。一个线程读到后面的标记时，其他线程可能仍在等内存槽、页锁或反向取页。因此只检查 TCP 顺序或者收到标记就回复，会过早宣布排空。

[PF18 补丁](../scripts/ssi-lab/experiments/kernel-dsm-inbound-drain.patch) 将读取下一帧与登记在途请求放在同一把分发锁内。页面处理可以并行；计数持续到响应发送返回、页锁释放及 SRCU 释放以后。标记持有分发锁等待计数归零，不持有页锁或 SRCU；此前请求仍可完成反向调用。标记后再出现页面请求或另一个标记，会触发协议错误。

代码复查还发现一个潜在竞态：识别坏帧后，如果先释放分发锁，再由调用者锁存故障，下一读者可能抢先确认后续标记。[PF19 补丁](../scripts/ssi-lab/experiments/kernel-dsm-drain-fault-order.patch) 在解锁前调用已有的首个错误锁存，关闭这段窗口。该竞态由源码审查发现；实测中，已进入 TCP 缓冲的标记仍被读到并记录 BEGIN，但首次故障锁存在先，未发送 ACK。连续发送坏帧和标记的实测属于修复后的拒绝验证，不能据此声称旧内核已经稳定复现过这个竞态。

## 实验协议与期限

| 字段 | 内容 |
| --- | --- |
| 请求 | 原有 x86 DSM 24 字节请求体，类型为 3 |
| 请求版本 | 1，与 QEMU 路由协议三分开 |
| 节点 | requester 和 msg_sender 必须一致且不是本地节点 |
| 关联序号 | gfn 字段承载非零 64 位值；只用于关联，不提供认证或跨会话防重放 |
| 确认 | 24 字节小端 `magic/version/sender/target/reserved/generation`，格式 `<IIHHIQ` |
| magic | `0x44534d44` |
| 元数据 | 回复原事务号，副本集合、页版本、保留字段和固定帧尾部清零 |
| 等待 | 标记进入处理器后，等待已有请求最多五秒；超时锁存 `ETIMEDOUT` |

五秒不是完整关闭上限。八个处理线程全被占用时，标记可能尚未读到；半帧接收、TCP 建连、确认发送也需要分别实现和验证期限。原有 EOF 仍然是错误。入站确认不证明对端已消费所有响应，不检查其他连接的缓存，也不禁止本 VM 的外部线程继续产生新请求。

## 实际验证

[证据](evidence/ssi-kernel-drain-20261106.json) 保存 PF18 的十二组有效探针、PF19 的八组补充探针，以及两个内核各自的单节点与双节点工作区回归。所有实验都有运行时哈希、构建来源和原始文件哈希。

| 场景 | 验证内容 |
| --- | --- |
| 空闲连接 | 确认的原始字节、事务号、节点和关联序号正确 |
| 七个缺页请求 | 延迟注册页面约 500 ms，期间没有确认；七份正确页面及各自页锁/SRCU 释放均早于确认 |
| 页锁等待 | 真实本地写入等待合成对端响应并持锁，另一请求和屏障等待；释放响应后内容与释放顺序正确 |
| 缺页超时 | 不注册页面，五秒等待结束后失败，处理线程在清理前退出，管理接口返回 EIO |
| 另一连接故障 | 屏障等待期间收到非法请求，不发送确认，保留首次协议错误 |
| 非法版本、零序号 | 拒绝标记，不产生排空确认 |
| 重复标记、后续新请求 | 第一次确认之后，第二次请求触发协议错误 |
| 坏帧紧接标记 | PF19 在同一次发送中收到坏帧和标记，先锁存坏帧错误，不能确认后续标记 |
| 八字节半帧 | 不产生确认，销毁 VM 可取消等待并回收处理线程 |

PF18 首次故障竞争记录只有十四个处理器返回，不能通过预期十六个的核查。故障可能打断新连接线程的创建或首次执行；探针现等待全部线程进入处理函数，再注入故障。随后一次尝试因 TCP TIME_WAIT 被前置检查拒绝，没有创建 KVM 实例；等连接自然回收后，第三次通过。两份未通过记录均保留，没有修改验收门槛。

[检查器](../scripts/ssi-lab/check-kernel-drain.py) 重新解析原始报文与完整内核跟踪，核对逐 CPU 丢失计数、kprobe 命中、线程退出、页面内容和阶段顺序。页锁释放使用真实返回探针，SRCU 释放必须来自 DSM 处理函数；其他子系统的 SRCU 事件不能代替它。异常的管理接口失效和线程退出必须发生在清理之前。检查器同时明确输出 `full_vm_shutdown_accepted: false`。

PF18/PF19 的普通单节点以及 PF18 双节点通过启动、三轮时钟、同进程内存、PAUSE 和 1 MiB SFTP 检查。PF19 双节点完成这些操作，十二个定时器最大约 33.76 ms，仍低于原 250 ms 门槛；但启动日志出现 `Long readout interval, skipping watchdog check`，因此启动检查拒绝这次记录，`operations_passed` 为 false。没有用后续时钟样本抹掉启动告警，也没有重跑挑选成功记录。该告警的原因和与候选的因果关系尚未确定。

两个内核的双节点 QEMU 屏障通过与内核 `-104` 同时保留；两端退出零不能代替正常 DSM 关闭验收。完整工作区、长期时钟稳定性和全 VM 关闭都仍有未通过项。

## 接下来仍要实现

全 VM 关闭需要原子停止新外部操作，统计发送至响应消费的完整事务，并保留服务线程完成反向取页所需的连接。只有所有节点都完成这些条件，再经过最终双方确认，才能把 EOF 作为正常结束。设备清理产生的后续内存访问必须位于最终关闭之前；不能在服务线程仍持有 SRCU 时盲目执行全局 SRCU 同步。

随后还需解决通用并发与设备 I/O、持久磁盘及 Ceph、Docker 和数据库一致性恢复、超过单机内存的工作集，以及不同物理机的性能与故障接管。两台 VM 同属一个 ESXi，不能提供物理故障域冗余。Ceph 只解决分布式存储的一部分，不能把普通 PostgreSQL 的执行内存变成跨主机透明共享内存。

## 复核与应用顺序

先阅读本文，再看 [入站屏障需求](../features/170-ssi-transport.feature)，然后检查保存的证据及探针。离线复核：

```sh
python3 scripts/ssi-lab/check-kernel-drain.py probe.json host.log
python3 -m unittest discover -s scripts/ssi-lab -p 'test_kernel_drain.py'
```

候选应用顺序为 PF17 → `kernel-dsm-inbound-drain.patch`（PF18）→ `kernel-dsm-drain-fault-order.patch`（PF19）。两份补丁都验证零 fuzz 重放与实际编译源一致，配置只改变内核版本后缀。默认安装流程不应用实验补丁。

探针只允许准确指定的 PF18/PF19 专用研究内核，拒绝已有实验进程、跟踪或相关端口的任何 TCP 状态。它不在普通 CI 中执行真实 KVM 实验；CI 重放证据并测试拒绝保护。实验结束后恢复原 Ubuntu 内核、原防火墙和空 GRUB 单次启动设置，移除本轮跟踪并停止临时构建 VM。公司的业务文件、生产服务与隧道没有参与实验。项目工具和文档使用 MIT；内核补丁保留 GPL-2.0-only。
