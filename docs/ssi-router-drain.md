# QEMU 关闭前的双向路由排空

2026-11-06。在 PF17 故障传播之后，继续实现正常关闭所需的 QEMU 屏障。**该屏障已经进入真实双节点实验，内核 DSM 的正常关闭仍未完成。** 同一物理 ESXi 上的两个专用 VM 运行一个内存客体，没有业务磁盘、Ceph、Docker 或数据库。

## 原路径的问题

原 `qemu_system_shutdown_request()` 只转发一个关机类型；对端将所有原因当作客体关机，路由线程随即退出。`qemu_cleanup()` 在块层排空之前关闭路由连接，既没有对端停止确认，也没有证明先前转发的操作已经执行。进程退出码为零不能证明跨节点排空，PF17 的正常关机依然记录内核 `-104`。

[候选补丁](../scripts/ssi-lab/experiments/qemu-router-drain.patch) 应用在已有 `qemu-dsm-failure-exit.patch` 之上，保留 PF17 内核。没有把传输 EOF 改成普遍成功，也没有删除内核错误日志。

## 实现的顺序与边界

1. 路由协议从 2 升到 3；关机通知携带真实原因与退出码，对端收到后继续服务路由。时钟启动握手也检查版本。混用旧版与新版的专门动态拒绝测试尚未完成。
2. 主线程经过 `vm_shutdown()`、`bdrv_drain_all_begin()` 和块任务取消后进入屏障。代码逐个确认此进程的四个逻辑 vCPU 已停止，记录本次序号，禁止后续普通转发产生新流量。每个进程的四个逻辑 CPU 包含远端占位，不能理解成每台实验 VM 都执行四个物理 CPU。
3. 向所有对端发送 `DRAIN`，再等待响应。请求包含协议版本、发送节点、接收节点和本次序号。对端在同一请求流中顺序处理先前操作，等本地也到达排空点才发确认。
4. 发送端核对确认标识、版本、双方节点与序号；本地既收到所有确认，又已向所有入站流发出确认，才能记录完成并关闭路由。确认后又出现请求、重复标记、缺失或不匹配的确认均走失败路径。
5. 屏障有独立 15 秒截止时间线程，网络等待不持该线程依赖的状态锁。提前到达的入站标记也有限时等待。它约束的是屏障阶段，**不覆盖之前暂停 vCPU 或排空块层可能发生的挂起**。

序号只用于同一 TCP 会话内关联确认，不是认证、加密或跨连接重放保护。上游入站路由仍没有完整身份认证；实验沿用专用 VM 的防火墙边界。两个节点之外的拓扑尚未动态验证。

## 实验结果

普通单节点完成 SSH、三轮时钟、内存、PAUSE、1 MiB SFTP 往返与关机，QEMU 返回 0，没有进入分布式屏障。

两次双节点正常对照分别用时 102.02 秒与 90.50 秒。两端日志均记录本地停止、发送确认、收到确认、完成屏障；跨节点序号对应，发送与接收确认的先后顺序在两次运行中不同。两个 QEMU 均返回 0。每次三轮定时器最大值分别为 **37.25 ms、229.23 ms**，保持原 **250 ms** 门槛；SSH、内存与文件内容校验通过。

从节点 1 向节点 0 的真实路由监听器发送完整但版本为 2 的 `DRAIN` 帧，节点 0 报 `SSI invalid drain marker`，两端 QEMU 返回 1，没有用关机完成记录掩盖失败。

另一组在客体仍运行、没有发出关机命令时发送版本与字段都正确的排空标记。前 500 ms 没有任何确认，连接保持等待；约 **15.06 秒**后节点 0 报本地排空截止时间到期，两端返回 1，没有 `SSI_DRAIN_ACK` 或完成记录。这验证了接收端等待本地条件，而非收到标记就立即确认；它不是“丢弃正常握手响应”的黑洞分区实验。

**上述正常对照的宿主仍记录 DSM 连接重置，完整关闭验收失败。** 排空记录只证明 QEMU 路由屏障，不证明内核页面事务已经完成显式关闭，也不证明文件系统刷盘、数据库提交或持久数据恢复。后续要在屏障之后接入内核关闭协议，并分别验证在途事务、取消、断连和超时。

## 复核与源码来源

[证据文件](evidence/ssi-router-drain-20261106.json) 保存每组的日志、运行时哈希、原始文件哈希、恢复记录和存储状态。[检查器](../scripts/ssi-lab/check-router-drain.py) 从两端原始事件重新匹配序号与顺序，拒绝单端确认、缺失事件、错误节点、未停止 CPU、过早完成和仅凭退出码判成功。已有 PF17 无屏障但返回零的记录用作拒绝对照。

首次构建引用了另一个源文件内的静态辅助函数而链接失败；改用本路由的节点索引后重新构建，无警告，零 fuzz 重放与编译源码一致。失败日志保留，失败产物未运行。QEMU 补丁遵循 GPL-2.0-or-later，原创探针检查与文档遵循 MIT。

错误确认回复、屏障期间的无 EOF 网络黑洞、混用版本、更多节点和真实持久 I/O 仍需动态故障注入。正常内核关闭、Ceph、容器与数据库、多台物理机的容量聚合和故障接管继续保留为未完成目标。
