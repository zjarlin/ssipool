# PF24：取页等待期间释放旧引用

PF24 让解除固定不再等待另一个固定调用持有的全局 DSM 锁或页面锁。旧引用可以先释放，让远端完成依赖该页面的请求，再返回新调用需要的页面。尚未完成的跨页固定使用暂存引用，外部解除不能消费它们。**这是完整设备关闭协议的一项前置修复，尚不提供整机关闭、持久化或故障接管。**

从 [需求场景](../features/150-ssi-device-memory.feature) 进入，再看 [补丁](../scripts/ssi-lab/experiments/kernel-dsm-pin-release.patch)、[探针](../scripts/ssi-lab/probe-pin-release.py)、[检查器](../scripts/ssi-lab/check-pin-release.py) 和 [原始证据](evidence/ssi-pin-release-20261106.json)。实验使用同一物理 ESXi 上的两台独占 x86 VM，直接调用真实 KVM，远端由回环协议对端控制。没有使用公司文件或业务磁盘。

## 已复现的依赖

PF23 的 MEMPIN 在等待远端页面时一直持有 `slots_lock` 和全局 `dsm_lock`。此时另一个线程要释放旧页面引用，也必须先拿到这些锁。如果远端需要旧页面才能交出新页面，两侧相互等待。

两台 PF23 实验 VM 都复现：新 pin 等待真实 `ktcp_receive`，unpin 在观察窗口内阻塞；只有探针主动交付取页响应，两者才继续完成。失败对照保留线程栈、事件顺序、原始 ioctl、网络帧和退出结果，没有强制重置实验机。

## 同步与引用变化

新 `dsm_pin_refs_lock` 只保护引用校验、暂存和提交，不跨越网络等待或页面锁等待。引用变化分为四步：

1. PREPARE 为已成功取得的页面增加有效引用和暂存计数。
2. 全段成功后 COMMIT 清除暂存计数，引用才允许被外部解除。
3. 中途失败则 ABORT 只撤销本次暂存引用。
4. RELEASE 只消费已提交引用；先检查整个范围，再修改计数。

全局 DSM 锁仍串行化固定调用，因此同时只有一个固定操作在建立暂存引用。解除路径不再取得该锁或页面锁，但仍在 SRCU 读侧保护下访问槽。固定调用短暂取得 `slots_lock`，等待之前的槽更新完成，再进入 SRCU 并释放槽锁；准入令牌从这之前一直持有到 SRCU 退出之后。

`kvm_dsm_has_pins()` 现在同时检查在途固定调用。即使第一张远端页面尚未到达、读写引用都为零，槽更新也返回 `EBUSY`，不能删除引用操作正在使用的映射。已有的全 VM 保守保护继续保留。

查询 ABI 没有改变。`read_refs` 和 `write_refs` 包括暂存保护引用，不等于可立即解除的引用数，更不是物理 `FOLL_PIN`、唯一页数或内存容量。无 DSM HVA 槽的范围仍按上游行为跳过；已存在 HVA 槽但没有客体反向映射返回 `EFAULT`。

## 验证方式

每个候选场景分别在两台 VM 上运行。检查器核对真实内核返回、准入令牌、完整操作区间、查询 ABI、网络帧与页面内容；要求解除或槽拒绝在远端响应发送之前完成，并在受控探针的 500 ms 观察门槛内返回。

| 模式 | 覆盖内容 |
| --- | --- |
| dependency | 旧引用释放后远端回调先返回页面，再交付新 pin 的远端响应 |
| pending | 读固定暂存期间可释放旧读引用，不能解除暂存或部分无匹配范围 |
| pending-write | 写固定的对应暂存保护 |
| empty | 首个远端页面尚未返回且引用为零，删除槽仍及时返回 EBUSY |
| rollback | 跨页取页之后遇到第三页反向映射缺失，只撤销本次暂存引用 |
| duplicate | 两线程同时解除一个旧引用，恰好一个成功，另一个返回 EINVAL |

普通 CI 重放保存的真实证据及篡改拒绝测试，不在 CI 宿主加载研究内核。历史 PF23 检查器与证据保持原样。完整客体回归独立运行普通单节点和双节点 SSH、时钟、共享内存、PAUSE、SFTP 及关机，继续使用原有 250 ms 时钟门槛。

12 组候选全部通过；2 组 PF23 阻塞对照也由检查器核验。候选的旧引用解除或槽拒绝最长为 0.109877 ms，仅代表这些受控测试。检查器不会把 empty 场景标为等待期间解除通过，因为它只在等待期间验证槽拒绝。

## 完整客体回归

使用同一 `qemu-system-x86_64-router-drain-1`，分别运行一次单节点和双节点，没有反复运行筛选更好结果。

| 项目 | 单节点 | 双节点 |
| --- | --- | --- |
| SSH、共享内存、PAUSE、1 MiB SFTP 往返 | 通过 | 通过 |
| 三轮定时器最大耗时 | 20.213431 ms | 123.725748 ms |
| 原 250 ms 时钟门槛 | 通过 | 通过 |
| QEMU 退出码 | 0 | 两端均为 0 |
| DSM 宿主关闭错误 | 无 | 两端均有 `ktcp_receive` 错误 |
| 完整 SSI 验收 | 不适用 | 失败 |

双节点启动日志和 QEMU 路由排空屏障通过，不能覆盖内核 DSM 的关闭错误。整个双节点实验耗时 90.27 秒，不是编译吞吐结果。PF23 的 264.93 ms 超限等历史失败继续保留；本次差异不能证明 PF24 提升了定时性能。

## 保留的探针失败

第二台 VM 的首次 pending 尝试在建立回环 TCP 时超时，尚未发出页面请求，也没有进入 pin 场景。跟踪和线程清理完成，失败记录没有替换为成功记录。

定向对照确认实验防火墙存在返回端口问题：仅放行回环目标 37710/37711 时，客户端显式绑定 40000 会因返回包目标落入受保护段而超时；补上同样仅限回环的源端口放行后，绑定 40001 可连接。控制脚本据此在探针期间双向放行回环流量，随后恢复精确原规则。首次失败没有保存随机源端口，因此不能断言该次一定由这个问题造成。修正后以新标签重新验证受影响场景，没有放宽内核或时钟门槛。

## 尚未完成

- 固定操作的全程截止时间、取消以及其他反向依赖组合仍未解决；500 ms 是当前探针门槛，不是内核提供的最坏时延承诺。
- 未覆盖动态引用溢出、32 位兼容调用、大规模槽重配置、真实设备复位、异步 DMA 或 IOMMU 生命周期。
- QEMU 尚未利用新增查询和入口封闭接口协调设备后台任务。最终 DSM CLOSE/ACK、半帧、建连、发送阻塞与确认丢失的完整关闭协议仍待实现。
- 本轮源码审查发现 QEMU 的 `address_space_map()` 在 MEMPIN 返回负数时仍继续返回 RAM 指针，解除失败也仅打印日志；新增待实现场景要求真实设备失败对照和正确失败传播。当前内核探针不能替代该修复。
- 尚未接入持久磁盘、Ceph、Docker、PostgreSQL、Redis 或 sub2api；没有跨物理机容量相加、性能相加或接管证据。

补丁在 PF23 后应用，为 GPL-2.0-only，单独构建 `-sshpool-gvm-pf24`。只修改两个内核源文件；零 fuzz 重放匹配实际编译源，配置只改变版本后缀，编译没有告警。默认构建流程不应用研究补丁；实验通过一次性 GRUB 启动，不改变原 Ubuntu 默认启动项。

实验结束后，两台节点均恢复 `6.8.0-147-generic`；旧启动文件哈希、`/lib` 链接和原防火墙一致，GRUB 一次性状态为空，无遗留实验进程或跟踪。Rust 格式、Clippy 与 14 项测试通过，Python 265 项测试通过，其中 15 项覆盖本轮证据及篡改拒绝。探针在不匹配内核上返回 2 且不创建输出文件。
