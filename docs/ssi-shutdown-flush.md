# QEMU 关闭时保留刷盘错误

当前研究 QEMU 的 `qemu_cleanup()` 忽略 `vm_shutdown()` 的返回值。后者包含设备停止通知、块层排空和最终刷盘；真实刷盘失败后，旧版仍继续路由排空并退出 0。候选补丁保留该返回值，直接向 stderr 写出错误并退出 1，防止把失败当成正常关闭。**这项修复不提供数据恢复、掉电持久性或完整 SSI 关闭。**

先读 [场景](../features/170-ssi-transport.feature)，再看 [QEMU 补丁](../scripts/ssi-lab/experiments/qemu-shutdown-flush-error.patch)、[探针](../scripts/ssi-lab/probe-shutdown-flush.py)、[检查器](../scripts/ssi-lab/check-shutdown-flush.py) 和 [真实证据](evidence/ssi-shutdown-flush-20261106.json)。补丁在上一轮映射失败候选之后应用，内核沿用 PF24；普通单节点也执行相同错误处理，没有更换客体内核。

## 真实故障对照

每次测试只在新目录创建独立 64 MiB 稀疏文件，使用 `raw → blkdebug → file` 的写回缓存链路并挂到测试 virtio 块设备。通过 QEMU 原生 HMP `qemu-io` 写入 64 KiB 非 FUA 数据，再读回检查内容；关闭时由原生 `blkdebug` 的 `flush_to_disk` 事件注入 `EIO` 或 `ENOSPC`。不是伪造 `vm_shutdown()` 的返回值，也没有使用已有业务盘。

QEMU 的 `blk_co_pwritev` 与 `vm_stop_flush_all` 原生跟踪分别证明写入和最终刷盘返回。QMP 记录核对真实设备、缓存没有绕过刷盘、写入范围和关闭请求；最终结果来自实际进程退出。**读回成功只证明缓存中的内容，不证明断电后数据仍在。** HMP 直接写 BlockBackend，没有走客体驱动的 virtio 描述符或 DMA 请求路径，不能据此验收那条路径。

| 对照 | 真实结果 |
| --- | --- |
| 两台原版内核 VM，各运行旧版正常与错误场景，共 4 组 | 正常刷盘退出 0；`-5` 和 `-28` 也错误地退出 0 |
| 两台原版内核 VM，各运行候选正常与错误场景，共 4 组 | 正常退出 0；错误保留到 stderr 并退出 1 |
| 两组 PF24 暂停双节点旧版，分别在节点零/一注入故障 | 本端原生跟踪分别返回 `-5` / `-28`，两端仍退出 `[0, 0]` |
| 两组 PF24 暂停双节点候选，分别在节点零/一注入故障 | 两端均退出 `[1, 1]`，没有正常路由排空完成标记 |
| 一组 PF24 暂停双节点候选，无故障 | 两端刷盘返回 0，退出 `[0, 0]` |

配对实例仍在同一 ESXi 的两台实验 VM 上。每个进程各有独立测试文件，**它们不是分布式磁盘副本**。节点一由节点零的关闭通知触发，未单独发第二个 quit 来伪造错误传播。两端共享原有故障停止机制；失败停止不尝试把不可信数据恢复成成功状态。

最早的候选单节点 EIO 实验已正确失败退出，但采集器没有处理 QMP 在回复前被复位，导致该次采集不完整。原记录保留并拒绝验收。后续采集明确区分正常回复、EOF 和连接复位，仍必须核对原生刷盘错误、日志和实际退出码，不能仅靠连接关闭判定成功。

## 数据边界与复现

探针拒绝复用已有目录，也拒绝冒号、逗号或换行改变 QEMU 参数解析；不接受直接传入已有磁盘。两个拒绝路径均在真实实验宿主验证，原实验盘和记录哈希保持不变。所有使用过的采集版本保留源码与哈希：最初版本不处理 QMP 复位，第二版用于完整矩阵，最终版增加目录分隔符保护并完成真实宿主拒绝验证。

单节点调用形式：

```sh
python3 probe-shutdown-flush.py \
  --qemu /path/to/qemu-system-x86_64-shutdown-flush-1 \
  --require-sha256 <实际运行时SHA256> \
  --require-kernel 6.8.0-147-generic \
  --firmware /path/to/pc-bios --error 5 \
  --directory /path/to/new-private-case
```

`--error 0` 是正常对照，`28` 是空间不足。配对模式还要求 PF24、`--node 0|1` 和 `--peers <两端地址>`；两个 READY 都到达后，协调器只向节点零 stdin 写 `quit`，节点一写 `wait`。超时或强制清理的记录必须拒绝。探针只清理自己创建的进程，保存错误和完整证据，不重置宿主。

检查器接受 `run + record` 的单节点记录或 `run + records` 的双节点记录；公开证据中的条目可直接重放。CI 做证据重放、篡改拒绝及错误内核拒绝测试，不在 CI 安装研究内核。

## 完整关闭仍缺什么

`vm_shutdown()` 的设备停止通知失败没有单独动态注入，本轮只验证真实块层 flush 错误。普通单节点和双节点完整客体各运行一次，SSH、共享内存、PAUSE、1 MiB SFTP 往返通过；三轮时钟最大分别为 20.176120 ms 和 104.895785 ms，低于未更改的 250 ms 门槛。QEMU 分别退出 `[0]` 与 `[0, 0]`，但双节点两端仍有 `ktcp_receive` 关闭错误，完整 SSI 仍未通过。没有降低阈值或挑选重复运行；这不是编译吞吐测试，也不能推断补丁改善了时钟性能。客体仍无持久卷，不把这些操作当成数据库验收。

源码审计确认网络层已有停止时清空队列的回调，不能仅凭 `net_cleanup()` 保留 NIC 就断言它泄漏。另一方面，virtio-blk 在 `BLOCK_ERROR_ACTION_STOP` 时把待完成请求保存在 `s->rq`；reset 会在排空后解除这些元素，但现有整机关闭并没有完整的 qdev unrealize。**这只是需要验证的生命周期缺口，不是已经动态复现的泄漏。** 下一步须用真实设备请求观察暂停、复位、销毁和关闭时的 DSM 引用，并保留历史 I/O 错误。

最终还需要所有设备生产者停止、KVM 准入封闭、全局代际和 DSM CLOSE/ACK、有界取消与恢复协议。不能通过移动断连调用或隐藏 EOF 错误声称完成。Ceph、持久磁盘掉电测试、Docker、PostgreSQL、Redis、sub2api、跨物理机容量相加和接管仍未验收。
