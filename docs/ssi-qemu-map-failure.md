# QEMU 的 DSM 映射失败停止

`address_space_map()` 在真实 `KVM_DSM_MEMPIN` 失败时仍交出 RAM 指针，`address_space_unmap()` 也会在解除失败后继续返回。候选补丁把这两条路径改为保留 stderr 错误、平衡本次 QEMU 内存区域引用，并以失败码退出当前节点。**这是一项失败停止修复，不提供正常关闭或故障接管。**

入口是 [设备场景](../features/150-ssi-device-memory.feature)，实现见 [生产候选补丁](../scripts/ssi-lab/experiments/qemu-dsm-map-failure.patch)，验证使用独立的 [诊断补丁](../scripts/ssi-lab/experiments/qemu-map-probe.patch)、[采集器](../scripts/ssi-lab/probe-qemu-map.py) 和 [检查器](../scripts/ssi-lab/check-qemu-map.py)。证据保存在 [原始记录](evidence/ssi-qemu-map-failure-20261106.json)。

## 失败语义与实验范围

只返回空指针会进入部分 DMA 调用者的映射重试等待，而永久 DSM 错误没有恢复通知。当前实现选择失败停止：map 分支先清零长度、清除 DSM 标记并撤销刚增加的区域引用；unmap 分支撤销映射持有的区域引用。随后输出失败码并退出，禁止把失败返回成可继续使用的映射或成功清理。

这不是完整设备回滚。错误发生后不承诺磁盘刷盘、客体文件系统干净、远端自动恢复或退出有统一截止时间。真实设备的 reset/unrealize、后台回调、IOMMU/直通 DMA 生命周期仍待验证。

实验只在同一物理 ESXi 的两台独占 x86 VM 中运行，宿主内核保持 PF24。诊断 QEMU 使用 `-S` 暂停、无磁盘、不运行客体代码，每节点承载四个 vCPU 中的两个。HMP 入口还要求显式 `SSHPOOL_LAB_MAP_PROBE=1`，每个进程只能使用一次；它不包含在普通候选二进制中。

| 模式 | 真实触发方式 | 核对内容 |
| --- | --- | --- |
| 0 | 读映射及解除，无故障注入 | 成功返回、内核引用归零、QEMU 引用平衡 |
| 1 / 2 | 真实封闭普通 KVM ioctl 后申请 4 KiB 读 / 8 KiB 写映射 | `-ESHUTDOWN` 后不能返回成功映射 |
| 3 / 4 | 成功映射后用真实 ioctl 消费固定引用，再调用实际 unmap | `-EINVAL` 后不能继续返回成功清理 |

模式 3/4 是受控的重复解除诊断，不宣称生产设备自然出现了相同竞态。所有模式都调用真实 QEMU 地址空间 API 和真实 KVM ioctl；没有用 mock 伪造错误。

采集器在 `kvm_vm_ioctl` 的入口和返回处核对命令、读写方向、解除标记、地址、长度和返回值。检查器同时要求 QEMU 的实际控制流、引用数、SSH 进程退出码、QMP 关闭以及无漏采的完整跟踪。QMP 复位本身不是通过依据，仍须看到实际进程退出。

## 诊断结果与保留的失败尝试

两节点各两组旧版读映射/解除失败对照，共四组；候选每节点五组，共十组，全部经原始证据检查器核验。候选正常对照退出 0，故障模式在被测节点退出 1，失败路径未继续返回，区域引用恢复到初始值。读写测试分别覆盖 4 KiB 与 8 KiB；这不是任意长度或所有并发设备的证明。

- 最早的基线诊断构建遗漏 runstate 头文件，产生编译告警。该二进制没有用于实验；补齐头文件后的基线、候选诊断和普通候选均独立构建。
- 第一轮无法注册已被内联的 `kvm_dsm_mempin` 探针，诊断没有执行。保留失败记录，通过 QMP quit 结束两台暂停实例，随后核查无遗留任务。
- 第二轮已经复现错误映射，但采集器未处理 QEMU 退出造成的 QMP 连接复位，缺少完成阶段，不能验收。
- 首个失败停止候选确实退出且平衡引用，但 `error_report()` 在 monitor 上下文缓冲，致命日志丢失。改成直接写 stderr 后重新构建，两套旧哈希和失败证据均保留。

## 普通候选的完整客体回归

使用不含诊断命令的候选运行一次普通单节点和一次双节点客体，PF24 内核不变。两次 SSH、共享内存、PAUSE 与 1 MiB SFTP 往返校验通过，QEMU 分别退出 `[0]` 和 `[0, 0]`。每次运行三轮时钟测试，继续使用原有 250 ms 门槛。

| 运行 | 最大定时器耗时 | 启动和操作 | 宿主关闭 |
| --- | ---: | --- | --- |
| 单节点 | 20.188975 ms | 通过 | 本次日志无检查器命中错误 |
| 双节点 | 96.470122 ms | 通过 | 两端均有 `ktcp_receive` 错误 |

双节点的 QEMU 路由排空屏障通过，**内核 DSM 关闭仍未通过**，不能用退出码零替代整机验收。该次双节点实验总耗时 98.49 秒，包含启动、操作和关闭；不是编译性能数据，也不能据此声称映射补丁加速了定时器。历史失败继续保留，没有降低阈值或重复挑选最佳成绩。

实验后恢复两台 VM 的原 Ubuntu 默认内核，并核对原有引导文件、机器身份、防火墙及无遗留 QEMU/DSM/跟踪任务；完整结果随证据保存。没有修改生产主机、业务磁盘、数据库或隧道。

## 复现与下一步

在现有 `qemu-router-drain.patch` 候选上应用生产补丁；内核沿用 [PF24](ssi-pin-release.md)。另建诊断变体时才应用 `qemu-map-probe.patch`。两个补丁均为 GPL-2.0-or-later，默认构建路径不自动应用。生产和诊断补丁均以零 fuzz 重放并与实际编译源码逐字核对。

暂停配对实例建立后，在目标实验节点运行：

```sh
sudo python3 probe-qemu-map.py \
  --require-kernel 7.1.0-rc3-sshpool-gvm-pf24 \
  --require-sha256 <该诊断二进制的精确哈希> \
  --pid <实际QEMU进程号> --qmp <该实例的Unix套接字> \
  --mode 1 --output <新的证据文件>
```

`check-qemu-map.py` 接受包含 `run`、`record` 和两个 `qemu_stderr` 的 JSON；公开证据的每条 `probes` 记录可以直接交给它。CI 只重放真实记录与篡改拒绝测试，并验证错误内核下拒绝执行，不在 CI 安装研究内核。

下一步仍须协调完整设备停止、取消和最终 DSM CLOSE/ACK，不能仅移动断连调用就声称所有设备已排空。Ceph、持久磁盘、Docker、PostgreSQL、Redis、sub2api、跨物理机容量汇聚和接管均未完成；新硬件的准入约束见 [物理机与存储](ssi-physical-storage.md)。
