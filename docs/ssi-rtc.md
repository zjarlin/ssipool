# RTC：分布式 PIO 与本地合并缓冲

2026-11-06。双节点客体的 RTC 错误有一条可复现的设备路由原因：索引写入被本地合并缓冲接收，数据读取却转发给另一节点的设备。候选 QEMU 禁用分布式客体的合并 PIO 注册，让索引写入也进入已有转发路径。独立时钟窗口对照通过，**这不是完整 SSI、持久存储或数据库验收**。

实验仍是同一物理 ESXi 上的两个专用 x86 VM，使用 PF15 研究内核及显式 PAUSE 拦截。客体无磁盘，没有接入 Ceph、Docker、PostgreSQL、Redis 或 sub2api。不能据此证明跨物理机容量相加或故障接管。

## 源码路径与修正

`mc146818rtc.c` 将 RTC 索引端口 `0x70` 注册为合并 PIO 区域。远端 QEMU 的 `kvm_handle_io()` 把数据端口 `0x71` 的读取转给根节点，绕过本地地址空间访问；`kvm_flush_coalesced_mmio_buffer()` 则把缓冲内的 PIO 写入交给本节点的 `address_space_io`。因此，根节点可能没有收到对应索引，读取的是旧寄存器。实测曾在远端 CPU 的所有日期分量读到重复数值，组成合法却错误的 `2004-04-04 04:04:04`。

[候选补丁](../scripts/ssi-lab/experiments/qemu-dsm-pio-coalescing.patch) 只修改 PIO 区域的添加、删除回调：当 `local_cpus != smp.cpus` 时不向 KVM 注册合并 PIO 区域。普通单节点保留原行为。检查放在内存监听器回调中，因为 `kvm_init()` 早于分布式拓扑初始化，不能在那里使用尚未就绪的 `local_cpus`。

补丁在已有 MMIO 完成确认候选上构建，没有改变路由协议，也没有增加 PIO 写完成确认。它不修复合并 MMIO、通用设备屏障或跨方向回调。源码零 fuzz 重放与实际编译源码一致，运行二进制哈希在每次实验前校验。

## 独立时间基准

[只读探针](../scripts/ssi-lab/guest-rtc.c) 仅在带显式标记的四 CPU 无磁盘客体中作为 PID 1 运行。它按 `0,2,1,3` 顺序切换 CPU，八轮共读取 32 次 `RTC_RD_TIME`，记录 ioctl 状态、实际 CPU 和完整年月日时分秒。CPU 0/1 在节点 0，CPU 2/3 在节点 1。探针不设置 RTC。

最初版本只检查字段范围，曾把合法的错误日期算作成功。两份初步记录保留，但不作为验收。正式检查器要求控制端记录开始、结束时间，并独立采集两宿主时钟；宿主时间必须落在请求区间附近一秒内，每次 RTC 读取必须落在实验窗口附近两秒内。缺失或重复样本、CPU 错序、汇总不符和错误时钟基准均拒绝。

| 实验 | 32 次读取中的失败数 | 说明 |
| --- | ---: | --- |
| 原版本单节点 | 0 | 有独立时间基准 |
| 原版本双节点 | 32 | 10 次 ioctl/日历失败，22 次合法但不在时间窗口内 |
| 候选单节点 | 0 | 普通路径对照 |
| 候选双节点 | 0 | 无系统调用跟踪 |
| 原版本双节点 + strace | 16 | 远端 CPU 各失败 8 次 |
| 候选双节点 + strace | 0 | 设备注册行为对照 |
| 候选单节点 + strace | 0 | 保留原合并注册行为 |

这只覆盖秒级 RTC 读取。窗口包含启动和日志收集时间，不能用于证明亚秒精度、频率漂移、RTC 中断送达或长期时钟稳定。

## 注册调用的证据边界

两端都实际报告支持 `KVM_CAP_COALESCED_PIO`。双节点基线每侧有四次成功注册、一次成功注销；候选两侧均为零。`strace` 将区域参数打印成指针，没有解码端口、长度与 PIO 标志，因此这些日志**不能单独证明某条 ioctl 的端口是 `0x70`**。RTC 端口来自源码核查，注册次数与日期对照是另外两项证据。

候选单节点仍有四次成功注册、一次成功注销，32 次读取通过。这个对照验证了当前机器模型的普通路径，没有覆盖其他设备组合和热插拔。

## 完整工作区仍不稳定

第一次无跟踪回归完成 SSH、三轮时钟、内存、用户态 PAUSE 和 1 MiB SFTP 往返。12 个请求 20 ms 的定时器最长 **66.615 ms**，低于未改动的 250 ms 门槛；串口 RTC 日期正常，没有 watchdog 跳过检查。客体发出断电、两个 QEMU 退出，但宿主仍有 DSM 接收 `-104` / `-4`，不能称为干净关闭。

第二次独立启动的日期正常，但报 `hpet: Lost 5 RTC interrupts`，随后在 SSH 认证后停止响应。节点 0 报 `ivy.c:439` 的 `WARN_ON_ONCE`，DSM 服务线程以 `-22` 退出。对应源码检查的是读页处理分支中，本节点是否还在页副本集合内；退出线程后，两个节点各有 vCPU 停在接收等待。已保存告警、线程栈、阶段失败与实际二进制哈希。**没有取得第二轮时钟、内存或文件传输通过记录，RTC 中断仍未通过。**

这里确认了失败位置，尚未确定是状态转换错误、并发竞争，还是该检查与协议不一致，也不能仅凭一次出现就归因于 PIO 修正。没有删除一致性检查或强行补位来掩盖问题。正常客体关机和 SIGTERM 均未释放这次实验，最后对身份和可执行文件哈希已核对的两个 QEMU 发 SIGKILL；此轮退出记为强制清理，不是正常关闭。VM 没有因 SSH 超时直接重置。

两轮完整记录见 [公开证据](evidence/ssi-rtc-20261106.json)。首次通过部分操作不能覆盖第二次失败。下一步需要可复现的页副本集合状态转换实验，以及异常请求向等待端传播失败的协议；正常关闭、通用 PIO 完成、持久 I/O、容器、数据库与故障接管仍需各自验收。

## 重放与实验恢复

```sh
python3 scripts/ssi-lab/check-rtc.py node0-qemu.log --reference result.json
python3 -m unittest discover -s scripts/ssi-lab -p 'test_rtc*.py'
```

对于预期失败的基线，可用 `--expect-failures N` 检查失败数；工具明确输出失败数，不能把命令成功视为 RTC 通过。公开证据保留完整探针记录、独立时间采样、运行时哈希与脱敏工作区日志；完整 ioctl 跟踪留在私有实验目录，公开摘录只用于复核注册次数。候选不进入默认安装流程。

实验结束后恢复默认 Ubuntu，核对身份、原防火墙、空 GRUB 环境及无 QEMU/DSM/跟踪残留；研究文件保留。恢复状态与存储检查记录在同一证据文件中。
