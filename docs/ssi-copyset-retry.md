# PF16：固定页面重试时保留副本集合

2026-11-06。PF15 工作区在 SSH 认证后出现 `ivy.c:439` 告警和 DSM 服务线程 `-22` 退出。单页真实 KVM 实验将问题缩小到一个确定路径：设备固定页面使读请求进入重试，但请求循环提前清空了仍归本节点管理的页副本集合。PF16 只在请求实际完成时执行这项清理，原告警检查保留。

这项修正服务于单客体跨节点共享内存。实验依然只使用同一 ESXi 上的两个专用 x86 VM；没有接入 Ceph、持久磁盘、Docker 或业务数据库，也不能据此证明跨物理机容量或故障恢复。

## 原因与修改

`dsm_handle_read_req()` 在页面被只读固定时设置 `retry=true` 并返回；此时还没有执行所有权转移或发送页面。外层 `ivy_kvm_dsm_handle_req()` 却把所有非 INVALIDATE 的零返回都当成请求完成，调用 `dsm_clear_copyset()`，然后才释放锁、处理重试。

解除固定后，处理器仍认为本节点是所有者，但副本集合已被清空。读请求转移所有权时检查到集合内缺少本节点，返回 `-EINVAL`，服务线程退出；等待端未收到页面。这解释了一条能复现同一告警的路径，但历史工作区未记录完整页面状态轨迹，不能把它当作所有相似故障的唯一原因。

[补丁](../scripts/ssi-lab/experiments/kernel-dsm-copyset-retry.patch) 把清理条件改为 `!retry && req.req_type != DSM_REQ_INVALIDATE`。没有删除 WARN、强行补成员位或伪造响应。代码同时覆盖读、写请求的重试返回；本轮动态验收针对只读固定后的远端读请求，其他固定模式和多副本写入仍须单独验证。

PF16 基于 PF15，除内核版本后缀外配置一致，QEMU 保持已有 RTC 路由候选。补丁零 fuzz 重放与实际编译源码逐字节一致。构建、启动及运行前哈希见 [公开证据](evidence/ssi-copyset-retry-20261106.json)。候选不进入默认安装流程。

## 单页对照如何验证

[探针](../scripts/ssi-lab/probe-copyset-retry.py) 在每台实验 VM 独立创建一个无 vCPU、无磁盘的真实 KVM 实例，注册一页内存，经 DSM MEMCPY 写入确定内容以建立所有权。它用真实 MEMPIN 接口只读固定该页，通过回环连接发送一份完整的远端读请求。

跟踪记录 `dsm_lock_killable` 入口/返回和 `dsm_unlock`。至少两次服务线程取锁、解锁后，探针确认没有提前响应，再解除固定。验收要求同一服务线程操作同一个页面槽和页号，返回完整 4 KiB 内容、正确 SHA-256、副本集合、版本及事务号；不能只看 ioctl 或脚本返回零。

| 内核 / 每台 VM 的模式 | 节点 0 | 节点 1 |
| --- | --- | --- |
| PF15，不固定页面 | 正确返回页面 | 正确返回页面 |
| PF15，固定后重试 | 处理线程 `-22`，无页面响应 | 处理线程 `-22`，无页面响应 |
| PF16，不固定页面 | 正确返回页面 | 正确返回页面 |
| PF16，固定后重试 | 正确返回页面 | 正确返回页面 |

这些是每台 VM 上真实内核与合成协议对端的实验，不能冒充两个真实 KVM 实例同时竞争页面。完整双节点工作区是另一组回归。

检查器复核逐 CPU 缓冲计数、kprobe 遗漏、请求字节、阶段次序、锁配对和八个服务线程退出。读取结束后，探针主动关闭模拟连接，再关闭 VM；这一段可能记录 `-104`，原值保留。这项验收检查读请求与资源回收，不宣称已经实现正常 DSM 关闭握手。

首次尝试因实验防火墙未开放回环端口而超时，尚未发送请求；之后仅为本次探针临时放行回环地址，结束后逐条核对恢复原规则。首次带固定的跟踪曾溢出，完整顺序验收拒绝它。新版改为读取 kprobe 计数决定何时解除固定，避免反复导出高频 trace 扩大采集开销，并保留无丢失记录。失败尝试和源码版本哈希没有被成功重跑覆盖。

## 双节点工作区回归

两个真实 QEMU 实例分别运行客体 CPU 0/1 和 CPU 2/3，组成一个四 CPU Linux 客体。两次独立启动均完成 SSH、两轮分配的同进程共享内存压力测试、用户态 PAUSE 与 1 MiB SFTP 往返。各运行三轮时钟探针，每轮 32 次跨 CPU 采样及四个请求 20 ms 的定时器，最大实际耗时分别为 **93.537 ms、94.413 ms**，没有改变原来的 250 ms 上限。

两次都没有页副本集合 WARN、无效 RTC 日期、丢失 RTC 中断或 watchdog 跳过检查；这只是本轮短窗口结果，不消除历史失败或证明长期稳定。客体发出断电并且两个 QEMU 均退出，但宿主继续报告接收 `-104` / `-4`。**完整工作区验收仍失败，正常关闭协议尚未完成。** SSH 在断电时的 255 退出码与实际串口/QEMU 记录一起保存。

这些结果不支持吞吐接近多机总和、超单机内存容量或硬件故障接管的结论。下一步应完善失败与关闭传播，再继续存储和业务负载验收。

## 复核与剩余范围

```sh
python3 scripts/ssi-lab/check-copyset-retry.py probe.json
python3 scripts/ssi-lab/check-copyset-retry.py baseline.json --expect request_rejected_after_unpin
python3 -m unittest discover -s scripts/ssi-lab -p 'test_copyset_retry*.py'
```

`--expect` 允许复核已知基线失败，输出仍明确标为请求拒绝，不能算成功读取。公开证据包含完整的小型函数跟踪及工作区日志；历史溢出记录保留摘要和原始文件哈希。实验结束恢复原 Ubuntu、防火墙和 GRUB 环境，核对无 QEMU/DSM/跟踪残留，关闭临时构建 VM。

通用页所有权竞争、请求失败传播、正常关闭、RTC 中断、长期时钟、持久 I/O、容器、数据库和跨物理机故障恢复仍是独立门槛。修复一个重试路径没有完成这些目标。
