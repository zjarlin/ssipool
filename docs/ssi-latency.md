# DSM 页面交接延迟定位

2026-11-06。PF11 内核没有改动。本轮增加真实 KVM 页面探针、按线程配对的内核跟踪与离线验收，定位完整客体的慢取页。两个专用 VM 仍在同一台 ESXi，未接入 Ceph、持久盘、Docker 或业务数据库，不能证明跨物理机资源相加或故障接管。

## 已完成的对照

`probe-dsm-latency.c` 创建一个无 vCPU 的 KVM 实例，注册一个 4 KiB 页面，通过真实 DSM ioctl 读写。每次只计 ioctl 内的 `CLOCK_MONOTONIC_RAW` 耗时，排除控制端 SSH 往返。控制器独立重建页面内容和 FNV64 校验和；跟踪器保存 ioctl、页面锁、网络发送和接收的入口/返回。

每组先执行 32 轮、每轮五次操作：写者写入、写者读取、另一节点读取两次、写者再次读取。最后一次读取通常使用仍有效的共享副本，不能当作新的远端取页。随后每节点两个线程各写 256 次，全部结束后验证两边得到相同完整页面，且来自某个线程的最后一次写入。这不证明中间的每次并发写入都被另一个线程观察到，也不是吞吐扩展测试。

| 最终探针 | 顺序操作 | 并发写入 | 包含最终读的 ioctl 数 | ioctl 最大耗时 |
| --- | ---: | ---: | ---: | ---: |
| PF11 单节点对照 | 160 | 512 | 673 | 0.032451 ms |
| PF11 双节点 | 160 | 1,024 | 1,186 | 1.825289 ms |

最终单节点与双节点页面校验、线程内顺序和 ioctl 配对全部通过。两节点各 594 次 DSM ioctl，包括一次启用；没有遗漏探针、缓冲区丢失或未返回调用。双节点响应接收的最大耗时为 1.359 / 1.486 ms。空闲请求监听可等待约一秒，单独列为 `listener`，不能算作请求响应延迟。这里只覆盖这些采样，不给一般负载的延迟保证。

完整原始探针记录、内核事件、运行时哈希和重算结果见 [证据](evidence/ssi-latency-20261106.json)。两台实验机已恢复原版 Ubuntu，身份、`/lib -> usr/lib`、空 GRUB 一次性启动项、无残留实验进程/跟踪事件和防火墙原样恢复均已核对。

## 完整 Linux 客体仍然卡顿

保持原版 Ubuntu 客体、QEMU、initramfs 和 PF11 不变，附加跟踪时运行三次原有时钟探针。两侧跟踪都先停止，再导出任何大文件。第一轮曾先导出节点 0 的约 41 MiB 跟踪才停止节点 1，污染了后者窗口；保留其哈希与排除原因，不用它归因。后两轮通过完整事件数、单调时间、每 CPU 丢失计数和 kprobe missed 检查；窗口边缘缺入口/返回的调用单独报告，不用于计算完整耗时。

| 诊断运行 | 时钟命令耗时 | 两侧最长响应等待 | 20 ms 定时器最大耗时 | 完整工作区 |
| --- | ---: | --- | ---: | --- |
| pair-2 | 42.410 s | 7.819 s / 0.690 s | 43.414406 ms | 失败：watchdog 跳过检查 |
| pair-3 | 35.725 s | 0.769 s / 2.413 s | 197.238991 ms | 失败：RTC 日期非法、watchdog 跳过检查 |

两轮各 96 次时钟采样、12 个定时器通过原有 250 ms 定时器门槛；内存、1 MiB SFTP 回取和正常关机也通过。但应用 CPU 切换之间仍有长停顿，串口仍有 workqueue 耗时告警。主节点关闭仍记录连接重置，不能称为双方确认排空的关闭协议。诊断跟踪和抓包本身有开销；此前无跟踪运行中 20 ms 定时器耗时 2.354 秒的失败仍有效，见 [PF11 请求安全回归](ssi-request-safety.md)。

## 热点页与具体指令

使用与客体内核哈希匹配的 `System.map`，并核对客体以 `nokaslr` 启动。第三轮额外保存 `kvm_page_fault` 的客体 RIP 和物理地址，将缺页与同线程后续页面获取配对：

| 客体函数 | 访问对象 | 页面获取耗时 |
| --- | --- | ---: |
| `ktime_get+0x27` | 物理 `0x401b4c0`，对应 `tk_core` | 615.721 ms |
| `timekeeping_update+0xd7` | 物理 `0x401b3d0`，对应 `shadow_timekeeper+0x30` | 2,032.531 ms |
| `resched_curr+0x11a` | 动态页面 `0xf534`，未进一步确定对象 | 2,412.569 ms |

因此 `0x401b` 的确包含并被访问的计时数据，不再仅凭页号猜测。一个页面还包含其他对象，不能把它的所有等待都归给单一变量。页面、锁和网络调用相互嵌套，累计耗时是包含子调用的时间，不能相加当作 CPU 用量。

## TCP 确认与 DSM 消费之间还有等待

第三轮仅在节点 0 的实验接口抓 DSM 连接，使用非混杂模式和 160 字节截断：2,270,715 个包被捕获，内核报告丢失 0。它不包含每个完整页面载荷，也不能排除网卡卸载的影响。

选取节点 1 写 `0x401b` 的事务 49270。用连接方向、页面、事务号和该次 TCP 流位置区分事务号回绕后的同号请求：

- 节点 0 抓到包含该请求的 TCP 序列范围，共 4,110 字节。
- 8.116 ms 后，节点 0 已发出覆盖全部 4,110 字节的累计 ACK。
- ACK 后又等 2,020.218 ms，节点 0 才发送 DSM 响应。
- 同线程跟踪显示页面锁约 2 μs 即获得；此次延迟主要在 DSM 接收返回之前。另一个 `ktime_get` 慢请求则有约 615 ms 的页面锁等待，不能一概归因。

这证明被选中的请求有很长一段时间发生在 TCP 确认之后，不证明是调度饥饿、丢失唤醒或某个锁的缺陷。下一步要同时采集接收线程的唤醒/运行状态、宿主抢占情况和 MMU/TLB 等待，才能决定改动。此次未应用猜测性的 TCP_NODELAY、线程优先级或客体时钟替换。

完整客体跟踪约数百 MiB，抓包约 293 MiB，保留在私有实验目录；公共证据给出原始文件 SHA-256、检查结果和上述事务/指令摘录。它们不是公开的完整跟踪，不把摘要或摘录冒充全量回放证据。页面探针的原始事件则完整收录，可由 CI 重算。

## 复用方式

1. 阅读 `scripts/ssi-lab/probe-dsm-latency.c`，用 x86_64 Linux 工具链以 `-O2 -Wall -Wextra -Werror -static -pthread` 编译。
2. 在已核对身份、独占且预先隔离 DSM 端口的实验 VM 上放置二进制、`trace-dsm-latency.py` 和同目录的 `trace-teardown.py`。通过控制器 `--help` 配置明确的 SSH、节点地址、指定研究内核和全新输出路径；跟踪需要 root。错误内核会在创建 KVM 前拒绝执行。
3. 用 `check-dsm-latency.py --log RUN.jsonl --trace NODE0.json --trace NODE1.json` 重算页面和计时；单节点只传一个 trace。对 QEMU 附加窗口只传 `--trace`，报告边缘截断而不混入完整调用统计。

这些工具只验证明确范围内的行为。SSI 的长期稳定性、持久 I/O、Docker、数据库、跨物理机内存容量和接管仍待完成。
