# 复位后继续接收关闭与故障

修复前，分布式 QEMU 收到 RESET 后退出 `io_router_loop()` 并关闭接收通道。客体虽已完成设备复位，副节点却无法继续处理主节点的关闭通知和后续断连，采集器等待 40 秒后只能强制清理。候选保留复位后的接收循环；真实 EIO 对照、副节点收到三次 RESET 的 ENOSPC 对照、正常关闭和主 QEMU 被 SIGKILL 的场景均完成预期退出。

这只验证**已分别暂停的双节点客体在复位后关闭或因对端退出而失败停止**。复位后恢复运行、协调时钟、网络分区、持久存储恢复与接管仍未完成；两台实验 VM 仍属于同一物理 ESXi。

先看 [场景](../features/150-ssi-device-memory.feature)、[候选补丁](../scripts/ssi-lab/experiments/qemu-reset-router.patch)，再看 [采集器](../scripts/ssi-lab/probe-virtio-dsm-pins.py)、[检查器](../scripts/ssi-lab/check-reset-router.py) 和 [原始记录](evidence/ssi-reset-router-20261107.json)。补丁为 GPL-2.0-or-later，只应用于独占实验环境。

## 修复与证据

补丁删除处理循环末尾的 `type == RESET || type == EXIT` 退出分支，并在 RESET 处说明连接必须保留。EXIT 原有的进程退出行为未改动，普通关闭仍经过现有排空协议。消息格式和协议版本没有改变，两端仍必须部署相同候选，不能假设旧接收端也会保留连接。补丁零 fuzz 重放与实际源码一致，编译无告警。

本轮普通候选不包含页引用诊断 HMP。采集器使用 `--pin-query none`，明确记录没有观察原生引用，不能把空采样列表当作引用为零。它记录真实 QMP 回复和 RESET 事件、运行状态、块设备错误、virtqueue、原生请求 trace、磁盘内容、进程退出及单调时间，并增加 `/proc` 线程快照。

旧版副节点在首次复位后少了一个线程；候选保留已有线程并收到全部后续 RESET。线程名称没有标识出路由角色，因此**不将该匿名线程仅凭名字认定为路由线程**。判断修复原因还依赖已核对源码的单一改动、主节点发起的管理命令、副节点原生 `guest-reset` 事件，以及后续关闭和 EOF 的处理结果。没有使用伪造日志或另向副节点发送关闭命令。

每次仍使用真实 Linux 客体，逻辑节点零直接写入并 fsync 新建 64 MiB 稀疏盘的 4 KiB 区域；节点一有自己的独立空盘，没有配置活动队列。客体不挂载宿主目录。错误来自原生 blkdebug 单次 EIO／ENOSPC。

| 版本与动作 | 观察结果 | 实际退出码（主／副） |
| --- | --- | --- |
| 旧版 EIO → 暂停 → 一次复位 → quit | 副节点 40 秒超时，需要采集器 SIGTERM | 1／1，但副节点属于强制清理 |
| 候选 EIO → 暂停 → 一次复位 → quit | 两端自行失败退出，后端错误保留 | 1／1 |
| 候选 ENOSPC → 暂停 → 三次复位 → quit，交换实验 VM 角色 | 两边均观察到三次实际 RESET，两端自行失败退出 | 1／1 |
| 候选正常写入 → 暂停 → 三次复位 → quit | 数据匹配，双方完成正常退出 | 0／0 |
| 候选正常写入 → 暂停 → 三次复位 → 主进程 SIGKILL，交换角色 | 副节点主动报告 `SSI router EOF before acknowledged drain` | -9／1 |

四组候选均没有采集错误、强制清理或残留进程。副节点从自身开始等待到观察退出分别约 115、114、31、114 ms；这些是本次采集窗口，不是跨网络故障探测 SLA。SIGKILL 只针对采集器新建的主 QEMU 子进程，并单独记录故障注入，不能用未声明的外部终止来取得通过。

错误后的复位只取消请求。EIO／ENOSPC 盘上对应区域仍为零，最终 flush 成功也不能消除后端错误；正常写入场景内容匹配。节点一的文件始终为空，**没有实现磁盘复制、掉电持久化或数据库恢复**。

## 复现入口

复用 [设备引用实验的启动与标准输入协议](ssi-virtio-dsm-pins.md#复现入口)，两端使用普通候选并增加 `--pin-query none`。完成真实写入或错误暂停后，分别向两端发送 stop。每次只向主节点发送 `{"op":"qmp","name":"system_reset"}`，然后查询双方快照 `after_reset_1`，三次场景继续到 `after_reset_3`。必须在保存的原始 QMP 中观察到对应次数的主端 `host-qmp-system-reset` 和副端 `guest-reset`，只看到 prelaunch 状态不算完成。

最后保存 before_quit 快照，副节点发送 `{"op":"wait_exit"}`；主节点正常路径发送 `{"op":"quit"}`，断连场景发送 `{"op":"crash"}`。采集器等待自身创建的进程退出并记录 `exit_observed_ns`，40 秒超时就保留失败并清理实验进程。`check-reset-router.py <记录.json>` 校验两端原始记录，基线结果明确为 `reset_shutdown_verified=false`。

基线运行时 SHA256：`f2fd12e514efdeb7493dd482f4ab343dce72289b8a90b131aebe84e4dddd4540`；候选：`7ed4008cbe393138b82b7ec96a643347ea1a9e22ba05f927e943189b219d09fc`。两者都使用同一 PF24 内核和客体镜像。普通 SSH 客体的单节点／双节点回归与原内核恢复结果也记录在证据文件中。

普通候选各执行一次单节点和双节点工作区回归，SSH、同进程共享内存、用户态 PAUSE 和 1 MiB SFTP 均完成，QEMU 分别退出零和零／零；三轮计时最大约 20.20 ms 和 34.56 ms，通过原 250 ms 门槛。这不证明该生命周期补丁带来性能提升。双节点宿主仍有 DSM 关闭错误，因此完整 SSI 仍失败。

实验结束，两台 VM 恢复原版 `6.8.0-147-generic`；机器身份、原引导文件哈希、防火墙与 `/lib` 链接核对一致，无残留 QEMU、DSM 或跟踪任务。业务主机、公司磁盘与隧道未改动。

## 仍缺少的协议

本次复位前由外部协调器分别停止两端，复位后始终保持 prelaunch，没有执行 `cont`。现有冷启动时钟限制仍保留，不能据此宣称已支持 reset 后继续运行。全局复位代际、远端完成确认、运行中复位、长期漂移、静默网络中断和反向发起故障仍需独立实现与验证。

整机设备生产者停止、KVM 封闭、DSM CLOSE/ACK 和干净断连也没有由此完成。Ceph、跨物理资源合并、Docker、PostgreSQL、Redis、sub2api 迁移及自动接管仍未交付。
