# PF17：把 DSM 请求失败传播到 VM

2026-11-06。PF16 中，单个处理线程遇到非法请求会记录错误并退出，但共用连接和其他处理线程仍在运行。远端取页可能一直等待，管理接口也继续把 VM 当成可用。PF17 锁存第一次故障、中止连接并调用 KVM 自带的 VM 失效通知，让管理端收到 `EIO`。

这是 SSI 故障处理的一步。故障发生时停止整个受影响 VM，没有实现自动接管、内存重建或正常关闭握手。实验仍只在同一 ESXi 的两个专用 x86 VM 进行，不能证明多台物理机容量相加。Ceph、Docker、PostgreSQL、Redis 和 sub2api 均未接入本轮实验。

## 原因与修复

原 `ivy_kvm_dsm_handle_req()` 错误出口释放临时页面并返回，但根线程仍阻塞在 `accept()`，没有主动结束共享连接。等待端既收不到响应，也收不到 EOF。等到操作者关闭 VM 或模拟对端，才出现的错误不能算及时故障传播。

[候选补丁](../scripts/ssi-lab/experiments/kernel-dsm-failure-propagation.patch) 采用以下顺序：

1. 用原子比较交换锁存 VM 的首个错误；后来的取消或断连不覆盖它。
2. 通过 `kvm_vm_dead()` 通知 KVM 的 vCPU 和用户态管理接口，唤醒 DSM 根线程。
3. 根线程中止监听器、已发布的外连和已接收的连接，再取消并回收全部服务线程。连接只做 shutdown，仍由原生命周期释放，避免使用者尚未退出就释放 socket。
4. 收发接口检查连接错误；事务缓存也不能绕过错误检查。连接初始化与失败扫描竞争时，发布者会补做状态检查并中止新连接。

传输层保留真实错误，不将 EOF 改成成功。它同时修正了部分发送后出错却返回正数、被上层误当成完整发送的问题；该短写路径尚未做独立内核故障注入。原协议没有错误响应帧，远端只能得知连接失败，不能从 TCP EOF 获得对端的具体 errno。本地原始原因与管理端 `EIO` 分别保留。

这是相对 PF11 的明确行为变化：请求处理器的致命退出将使整个 VM 失效，不能在同一实例继续发送新请求。PF11 的“取消一个线程后其他请求继续成功”及“多个非法请求后同 VM 仍可读页”属于历史对照，相关 `.feature` 已标明内核版本。

PF17 基于 PF16，配置只改变版本后缀。内核补丁零 fuzz 重放与编译源码逐字节一致。一次构建因函数声明放在错误头文件失败，修正声明位置后构建成功；失败日志保留在私有实验记录中。直接接口探针不启动 QEMU；完整客体回归分别使用已有 RTC 路由候选与下述故障退出候选。默认安装流程不自动应用这些补丁。

## 真实 KVM 对照

[探针](../scripts/ssi-lab/probe-failure-propagation.py) 每次创建一个真实 KVM VM 和一个不运行客体指令的 vCPU，注册一页内存。合成对端先正常取得页面所有权，然后本地真实 `DSM_MEMCPY` 写调用向它请求页面；模拟对端暂不回复。第二条连接发送缺失内存槽的读请求，真实服务线程收到完整请求后才开始故障注入。

| 每台实验 VM 的场景 | PF16 | PF17 |
| --- | --- | --- |
| 非法请求类型 | 写调用和缺失槽请求仍等待 | 写调用返回 `EPROTO`，VM 失效 |
| 超容量请求 | 写调用和缺失槽请求仍等待 | 写调用返回 `EMSGSIZE`，VM 失效 |
| 对端断开 | 另一连接和写调用仍等待 | 写调用返回 `ECONNRESET`，VM 失效 |
| 正常页面响应 | 完成写入且寄存器可读 | 完成写入且寄存器可读 |

六次 PF17 故障对照中，本地在途写入从注入到返回约 **7.18–18.21 ms**，均在原定 500 ms 窗口内；17 个 DSM 线程全部在测试清理之前退出。`KVM_GET_REGS`、`KVM_RUN` 和 VM ioctl 均返回 `EIO`。基线在 500 ms 观察窗口结束时仍等待，清理关闭对端后才退出；原始时间和两类结果都有保留。正常对照按实际页面内容校验 SHA-256，没有用返回零代替内容检查。

这些直接探针是“真实 KVM + 合成对端”，不能冒充两个真实 KVM 之间的故障传播。[检查器](../scripts/ssi-lab/check-failure-propagation.py) 核对原始帧、线程身份、阶段顺序、逐 CPU 缓冲计数、kprobe 遗漏、全部线程返回与退出；拒绝把清理阶段的返回或摘要布尔值当成成功。

PF17 节点 0 的首次尝试在建立回环连接前超时，没有发送请求或完成故障注入，因此被拒绝并保留原始记录。其原因尚未确定；后续记录额外保存实际临时防火墙规则，不能据重跑成功推定首次超时原因。

## QEMU 报错递归与失败退出

旧 QEMU 在两个真实 KVM 组成的客体中完成 SSH、三轮时钟、内存、PAUSE 和 SFTP 后，向节点 0 的监听器注入非法类型请求。节点 0 锁存 `EPROTO`，节点 1 收到连接失败并锁存 `ECONNRESET`，两边都收到 KVM_RUN 错误。但错误报告本身递归调用 `cpu_dump_state()` → `cpu_synchronize_state()` → 读取已失效的 KVM 状态 → 再次 `cpu_dump_state()`，最终两边段错误。每端出现 **52,374 次** CPU 状态同步失败。这证明了错误传到 QEMU，同时也证明旧 QEMU 没有可控退出。

[QEMU 候选补丁](../scripts/ssi-lab/experiments/qemu-dsm-failure-exit.patch) 在 `kvm_cpu_exec()` 的致命错误出口检查分布式 CPU 拓扑，报告错误后调用 `exit(EXIT_FAILURE)`，避免再次读取失效状态。普通单节点保留原错误出口。第一次候选构建暴露重复局部变量的遮蔽警告；复用已有变量后重新构建无警告，补丁零 fuzz 重放与编译源码一致，两个版本的私有构建记录均保留。这里只覆盖该执行错误出口，不保证所有设备错误回调也已完成故障处理。

失败退出不会执行完整客体关机、文件系统刷盘或数据库提交，也不能恢复丢失页面。所有测试客体只使用内存文件系统，没有挂载业务磁盘。后续接入持久存储必须继续验证错误、刷新顺序和恢复语义。

| PF17 工作区 | 原 QEMU | 故障退出候选 |
| --- | --- | --- |
| 普通单节点 | 各操作通过，QEMU 返回 0，宿主日志通过 | 各操作通过，QEMU 返回 0，宿主日志通过 |
| 双节点正常运行与关机 | 各操作通过，定时器最大 69.45 ms，QEMU 返回 `[0, 0]`，关闭仍报 `-104` | 各操作通过，定时器最大 92.03 ms，QEMU 返回 `[0, 0]`，关闭仍报 `-104` |
| 双节点注入非法请求 | 命令与数据校验通过，定时器最大 206.96 ms，但启动已丢失 3 次 RTC 中断；两端递归报错并段错误，SSH 返回 `[255, 255]` | 注入前操作与启动日志通过，定时器最大 178.72 ms；两端明确失败退出 `[1, 1]`，没有递归或段错误 |

各组时钟均执行三轮，保持原 **250 ms** 门槛。新版故障组节点 0 的 KVM_RUN 返回协议错误，节点 1 返回连接重置；直接管理探针收到的 `EIO` 与这些执行路径的原始错误分开记录。故障注入阶段开始至控制器收尾约 0.33 秒，这包含 SSH 与日志管理，不能当作内核故障传播延迟。没有强制终止 QEMU。双节点正常关闭仍然失败，不能因为进程返回零就声称完成握手。

旧版故障组的 `Lost 3 RTC interrupts` 出现在 OpenSSH 就绪前，故该组启动门槛也失败，不能只依据各命令返回零给整个工作区标记成功。新版三组未观察到同一告警不等于已经修复 RTC 中断。两版故障组还保留页面获取失败的内核调用栈；旧版有创建连接线程被取消的 `-4`，它们均作为真实故障现场保留，不称为干净宿主日志。

完整记录见 [故障传播证据](evidence/ssi-failure-propagation-20261106.json)。旧版约 12 MB 的重复 stderr 按行与连续重复次数无损编码，包含原始文件哈希、字节数和脱敏后展开内容的哈希；检查器重建全文再判断，不能删掉段错误或只保留成功摘要。其他原始文件保留私有副本与公开哈希清单。

## 边界与复核

```sh
python3 scripts/ssi-lab/check-failure-propagation.py candidate.json
python3 scripts/ssi-lab/check-failure-propagation.py baseline.json --expect request_still_waiting
python3 scripts/ssi-lab/check-failure-propagation.py control.json --expect request_completed
```

实验需要专用 PF16/PF17 x86 VM、准确内核哈希、空闲 TCP 端口以及临时回环规则。控制端保存运行时哈希和防火墙前后对照，结束后恢复原 Ubuntu 并检查无实验残留。探针、检查器及原始实验数据的公开副本使用 MIT；内核补丁继续遵循 GPL-2.0-only，QEMU 补丁遵循 GPL-2.0-or-later。

新连接尚在阻塞式 TCP connect 的窗口、无 EOF 的黑洞分区、故障与页面所有权并发变化、协议认证和重放防护仍未完成验收。没有恢复已丢失内存、持久数据或失联节点；仍需显式关闭协议、存储和业务负载、跨物理机故障接管等后续门槛。
